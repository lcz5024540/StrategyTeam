# 输出文档 (Documentation Writing)

本技能保证 CoinStrategy 项目的技术文档**结构清晰、可读性强、便于他人快速理解**。

## 何时使用

- 写设计文档、方案文档、架构说明
- 写策略说明文档
- 写排查报告、复盘报告（也可结合 `troubleshooting` 技能）
- 写或更新 README
- 把一段分析/调研结果沉淀为正式文档

## 核心原则

1. **读者优先**：先想清楚「谁会读、读完要能做什么」，再决定详略和术语。
2. **结论先行**：重要结论放最前面，细节放后面，读者可逐层下钻。
3. **能画图就别堆字**：架构、流程、时序、状态用图表达远胜大段文字。
4. **可维护**：文档会过时，写清楚日期与版本，过时内容及时标注或更新。

## 标准文档结构

技术文档（设计/方案类）推荐如下骨架，可按需增删：

```
# 标题（一句话说清这是什么）

> 状态：草稿 / 评审中 / 已定稿   |   作者：xxx   |   日期：2026-05-23

## 1. 背景与问题
   - 当前现状、痛点、为什么现在要做

## 2. 目标与非目标
   - 目标：本次要达成什么（可衡量）
   - 非目标：明确不在范围内的，避免误解

## 3. 方案设计
   - 总体思路（配架构图）
   - 关键模块/接口/数据结构
   - 关键流程（配流程图/时序图）

## 4. 风险与权衡
   - 已知风险、对资金/线上的影响、缓解措施
   - 备选方案及未采用原因

## 5. 实施计划
   - 任务拆解、依赖、里程碑

## 6. 验证方式
   - 如何确认方案有效（测试、回测、灰度、监控指标）
```

排查/复盘类文档结构见 `troubleshooting` 技能。

## 可读性规范

### 标题层级
- 一篇文档只有一个 `#` 一级标题。
- 层级不超过 3~4 级，过深说明该拆文档了。
- 标题用名词短语，能让人扫一眼目录就懂全文脉络。

### 图表
- 架构、依赖关系、流程、时序优先用 **Mermaid**（项目已大量使用，GitHub/IDE 可直接渲染）：
  - 架构/依赖：`graph TD`
  - 流程：`flowchart`
  - 时序：`sequenceDiagram`
  - 状态机：`stateDiagram-v2`
- 多维对比用**表格**，不要用并列段落。
- 代码、配置、命令用代码块并标注语言。

### 文字
- 段落短，一段讲一件事。
- 关键术语首次出现给出定义或中英对照。
- 避免「显然」「众所周知」这类词，读者背景未必和你一样。
- 列举步骤用有序列表，并列项用无序列表。
- 涉及金额、阈值、参数务必写清单位与精度。

### 数字与事实
- 关键数字给出来源或计算口径。
- 不确定的内容标注「待确认」，不要伪装成结论。

## 存放与命名规范

- **设计/方案/架构文档**：放 `docs/` 下对应子目录（如 `docs/polymarket/`）。
- **策略说明文档**：放项目根或 `funding-rate/`、`polymarket/` 等策略目录。
- **排查/复盘报告**：放 `docs/` 或对应策略目录，文件名带日期。
- **模块说明**：放该模块目录下的 `README.md`。
- 文件命名：英文用 `kebab-case`（`capital-recycle-exit-design.md`）；带时间的报告统一加 `YYYY-MM-DD`。
- 文档之间用相对路径互相链接，形成可导航的文档网。

## 完成前自检清单

- [ ] 开头是否点明「这是什么 / 给谁看」？
- [ ] 重要结论是否前置？
- [ ] 架构/流程是否用图，而不是大段文字？
- [ ] 是否标注了状态、作者、日期？
- [ ] 术语、单位、精度是否清晰？
- [ ] 是否放到了正确目录、命名是否规范？
- [ ] 是否和相关文档建立了链接？

## 配套技能

- 长文档建议先用 superpowers 的 `writing-plans` 列大纲再填充。
- 整理已有散落文档成知识库时用 `obsidian-knowledge-base` 技能。
