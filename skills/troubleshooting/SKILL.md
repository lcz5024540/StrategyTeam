# 故障排查与复盘 (Troubleshooting & Retrospective)

CoinStrategy 是 7×24 运行的交易系统。本技能提供**系统化排查方法**和**复盘报告模板**，避免靠猜、避免同一个问题反复出现。项目中已有大量排查报告（`排查报告-2026-05-17.md`、`为什么还没开单-2026-05-18.md` 等），本技能统一其方法与格式。

## 何时使用

- 系统行为不符合预期：策略不开单、订单卡住、数据不更新、收益异常、服务报错。
- 用户问「为什么……」「排查一下」「定位问题」。
- 事故发生后需要复盘。

## 排查方法：先定位，再修复

### 第 0 步：抑制冲动，不要乱改
看到报错先别急着改代码。**未定位根因就改动，可能掩盖问题或引入新问题，对交易系统尤其危险。**
可结合 superpowers 的 `systematic-debugging` 技能。

### 第 1 步：明确现象
- 精确描述：什么不对？预期是什么、实际是什么？
- 量化：何时开始？影响范围多大？是否还在持续？
- 是否涉及资金/订单的实际损失？涉及则优先评估止损。

### 第 2 步：收集证据
- 日志：`logs/` 目录，关键路径日志、异常堆栈、时间线。
- 数据：数据库订单/持仓/收益记录、交易所实际状态。
- 配置：相关策略参数、限额、开关。
- 环境：服务是否存活、网络、交易所是否有公告/故障。
- **以事实为准**，不要用猜测代替证据。

### 第 3 步：建立假设并逐一验证
- 列出可能原因（按可能性 + 影响排序）。
- 一次只验证一个假设，用证据**证实或证伪**。
- 善用二分法缩小范围：是数据问题还是逻辑问题？是策略层还是适配层？是本地还是交易所侧？
- 能复现的问题优先做最小复现。

### 第 4 步：定位根因
- 找到能完整解释所有现象的根因，而不是表面症状。
- 区分「直接原因」和「根本原因」（如：直接原因是空指针，根本原因是上游数据契约未校验）。
- 根因没找到前，不算排查完成。

### 第 5 步：修复与验证
- 修复方案遵循 `coding-standards`，最小改动。
- 验证修复有效，且没有引入新问题（结合 `test-driven-development` 补测试防回归）。
- 涉及资金逻辑的修复，灰度验证后再全量。

## 排查报告模板

```markdown
# 排查报告 —— <问题简述> (YYYY-MM-DD)

## 1. 问题现象
预期 vs 实际，发生时间，影响范围。

## 2. 影响评估
是否有资金/订单损失，受影响策略/用户，严重程度。

## 3. 排查过程
- 假设 A → 验证 → 证伪（证据：...）
- 假设 B → 验证 → 证实（证据：...）

## 4. 根因
直接原因 + 根本原因。

## 5. 修复方案
改了什么，文件，如何验证。

## 6. 状态
已修复 / 灰度中 / 待观察。
```

## 复盘报告模板（事故事后）

排查解决问题，复盘是为了**不再发生同类问题**：

```markdown
# 复盘 —— <事故简述> (YYYY-MM-DD)

## 时间线
| 时间 | 事件 |
| --- | --- |
| HH:MM | 问题发生 |
| HH:MM | 发现 |
| HH:MM | 定位根因 |
| HH:MM | 修复完成 |

## 根因分析
连续追问「为什么」直到制度/设计层面的原因。

## 做得好的 / 做得差的
响应、定位、沟通中值得保留与需改进之处。

## 改进项（Action Items）
| 改进项 | 负责人 | 截止 | 类型（防发生/早发现/快恢复） |
| --- | --- | --- | --- |

## 经验沉淀
需要写入文档/监控/告警/checklist 的内容。
```

## 重要原则

- **根因导向**：没定位根因就改代码是排查大忌。
- **证据导向**：用日志和数据说话，不用猜测下结论。
- **不指责个人**：复盘对事不对人，聚焦系统和流程的改进。
- **闭环**：改进项要落到具体文档/监控/checklist，并跟踪完成。

## 配套技能

- 调试过程结合 superpowers 的 `systematic-debugging`。
- 报告成文用 `doc-writing`，存放规范见该技能。
- 排查涉及安全问题时叠加 `trading-security-audit`。
- 排查进度与结论用 `context-tracking` 记录。
