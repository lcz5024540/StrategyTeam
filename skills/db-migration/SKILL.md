# 数据库变更管理 (Database Migration)

CoinStrategy 的数据库存着订单、持仓、收益、策略配置等关键数据。表结构变更若处理不当会导致**线上服务报错、数据丢失**。本技能规范数据库变更流程。

## 何时使用

- 新增表、修改表结构、加/删字段、加索引。
- 编写 `sql/` 目录下的变更脚本。
- 审查别人的数据库变更。

## 一、变更脚本规范

### 存放与命名
- 所有变更脚本放 `sql/` 或对应子目录（如 `sql/polymarket/`）。
- 沿用项目现有命名约定：`YYYY-MM-DD__<简述>.sql`（如 `2026-05-17__p1_tracker_persistence.sql`）。
- 草稿用 `_draft` 后缀（项目已有先例），定稿后去掉。
- 一个脚本对应一组相关变更，不要把不相关的变更混在一个文件。

### 脚本内容
- 文件头注释写清：**目的、关联功能/issue、作者、日期、是否需停服、回滚方式**。
- DDL 语句加 `IF NOT EXISTS` / `IF EXISTS` 等保护，保证可重复执行（幂等）。
- 字段、表、索引都加注释（`COMMENT`），说明用途。
- DML（数据初始化/订正）与 DDL 尽量分开脚本，种子数据用独立 `_seed` 文件（项目已有先例）。

## 二、向后兼容（最重要）

变更期间「旧代码 + 新表」或「新代码 + 旧表」可能并存，必须保证不出错：

- **加字段**：新字段允许为 `NULL` 或带默认值，不要直接 `NOT NULL` 无默认值（会让旧 INSERT 失败）。
- **删字段/删表**：分两步 —— 先发布不再使用该字段的代码，确认无引用后，下一次变更再删。绝不和代码同批删。
- **改字段类型/重命名**：高风险。优先「新增字段 → 双写 → 迁移数据 → 切读 → 删旧字段」的渐进方式。
- **改约束**：加 `NOT NULL`/唯一约束前，先确认存量数据全部满足。

## 三、大表与性能

- 对大表做 DDL（加字段、加索引）可能锁表，评估数据量与影响，必要时安排低峰期或用在线 DDL 工具。
- 加索引前确认查询确实需要；评估对写入性能和存储的影响。
- 新查询上线前检查是否走索引，避免全表扫描。

## 四、回滚方案

- **每个变更脚本都要有对应的回滚 SQL**（或在脚本头写明回滚步骤）。
- 加字段的回滚是删字段；建表的回滚是删表；数据订正的回滚要能恢复原值。
- 不可逆的变更（如删字段、删数据）执行前**必须先备份**相关表/数据，并经用户确认。

## 五、变更审查清单

- [ ] 命名是否符合 `YYYY-MM-DD__描述.sql` 约定，放对目录？
- [ ] 脚本头是否写清目的、是否停服、回滚方式？
- [ ] DDL 是否幂等（`IF [NOT] EXISTS`）？
- [ ] 新字段是否可空或有默认值，不会破坏旧代码？
- [ ] 删字段/删表是否拆成了「先去引用，后删除」两步？
- [ ] 大表变更是否评估了锁表/性能影响？
- [ ] 是否有回滚方案？不可逆变更是否先备份？
- [ ] 表/字段/索引是否都有 `COMMENT`？
- [ ] 应用层实体/Mapper 是否同步更新？

## 重要原则

- **变更脚本与对应的代码改动配套提交**，commit 用 `build(sql)` 或 `feat(<scope>)` 并在 body 说明（见 `git-commit-convention`）。
- 生产环境执行任何变更前**先在测试环境验证**。
- 删除类、数据订正类操作执行前**必须经用户明确确认并备份**。
- 不直接在生产数据库手敲 SQL —— 一切走脚本，留痕可追溯。

## 配套技能

- 变更脚本的提交用 `git-commit-convention`。
- 变更涉及敏感数据（密钥、用户资产）时叠加 `trading-security-audit`。
- 变更设计文档用 `doc-writing`。
