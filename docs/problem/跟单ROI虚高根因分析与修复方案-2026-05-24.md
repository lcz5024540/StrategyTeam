## 一、结论先行

我方持仓的"盈利比例"（`roiRate`）被算成了 **347.74%**，但真实行情只涨了约 30%。

**根因：我方持仓被按"中标全额赔付价 \$1.00"估值/结算，而不是按真实市场现价估值。** 此时前端显示的"盈利比例"实际上等于这笔押注的**理论最大赔付率 `(1 − 入场价) / 入场价`**，而不是真实盈亏率。

这一结论可由用户给出的三个数字精确反推、且完全自洽（详见第三节）：

| 量 | 反推值 | 说明 |
|---|---|---|
| 我方入场价 `p` | **0.2233** | 由 `(1−p)/p = 347.74%` 反解 —— 是个完全正常的跟单买入价 |
| 真实市场现价 `M` | **0.290** | `p × 1.30`，对应"市场涨了 30% 多" |
| 跟单地址入场价 `L` | **0.151** | 由跟单地址 ROI `M/L−1 = 91.67%` 反解 |
| 价格次序 | `L 0.151 < p 0.223 < M 0.290` ✅ | 领单地址最早最便宜买入，我们晚一步以更高价跟入，现价又更高——**完全合理** |

关键点：**反推出的我方入场价 0.2233 是正常的、且高于领单地址的 0.151（符合"跟单晚于领单"的物理常识）。说明入场价本身没错，错的是给这笔持仓估值时用的"现价"——它被当成了 \$1.00。**

- 我方**真实** ROI 应为 `M/p − 1 = 0.290/0.223 − 1 ≈ 30%`；
- 系统**显示** ROI 为 `1.00/p − 1 = (1−p)/p ≈ 347.74%`；
- 虚高倍数 ≈ **11.6 倍**。

跟单地址的 91.67% 由另一条完全独立的代码链路（`WalletOrderAggregationService`，基于真实成交价）计算，**数值正常**，可作为"正确口径"的对照基线。问题 100% 出在我方持仓的估值/结算侧。

## 二、"盈利比例"是怎么算出来的（已核对代码链路）

前端跟单页 `TradesTable` 第 203 行 `formatPercent(trade.roiRate)` 直接展示后端 `roiRate`；`format.ts` 的 `formatPercent` 只是 `× 100`。所以 347.74% 意味着后端 `roiRate = 3.4774`。

后端 `roiRate` 有两处计算，公式一致：

```
roiRate   = totalPnl / roiBase
totalPnl  = realizedPnlUsdc + unrealizedPnlUsdc
roiBase   = entryCost（入场成本）
```

- `SmartWalletAccountingService.toTradeView()` 第 4646–4652 行；
- `SmartWalletTradeOrderService.buildTradeOrder()` 第 501–516 行。

对一笔**正常的 PAPER 跟单持仓**（当前线上全部为 PAPER 模式），把链路展开后会发现 `roiRate` 必然等于一个很干净的式子：

1. 入场：`recordExecution()` 第 144–146 行，`price = result.getPrice()`、`notional = recommendedStakeUsdc`、`size = deriveSize(notional, price) = notional/price`。
2. 成交：`executeFillAndAccounting()` 第 459 行，`fill.notional = size × price = notional`。
3. 建仓：`applyFillToPosition()` 第 2801–2823 行，`quantity = size`、`costBasisUsdc = notional`、`averageEntryPrice = price`。
4. 估值：`markToMarket()` 第 3266 行，`unrealizedPnl = markPrice × quantity − costBasisUsdc`。

代入（持仓未平仓时 `realized = 0`、`roiBase = entryCost = notional`）：

```
roiRate = unrealizedPnl / notional
        = (markPrice × quantity − costBasisUsdc) / notional
        = (markPrice × (notional/price) − notional) / notional
        = markPrice / price − 1
```

**即：盈利比例 = 估值用的 markPrice ÷ 入场价 price − 1。**

- `price`（入场价）= 跟单买入时点的盘口卖一价，由 `resolveFreshEntryPrice()` 抓取，正常落在 0–1；
- `markPrice`（估值价）= `markToMarket()` 抓的盘口买一价，正常也落在 0–1；
- 正常情况下两者都是同一 token 的盘口价，`roiRate` 就是真实涨跌幅。

要让 `roiRate` 冲到 3.4774，必须 `markPrice / price = 4.4774`。而 `markPrice` 最高只能是 \$1.00。**只有当 `markPrice` 被当成了 \$1.00（中标全额赔付价），且 `price ≈ 0.223` 时，才会恰好得到 347.74%。** 这就是"按全额赔付估值"的数学指纹。

> 已平仓/已结算口径同理：`roiRate = realized / entryCost`，结算时 `realized = quantity × resolutionPrice − costBasis`；若 `resolutionPrice = 1.0`，则 `roiRate = (1−p)/p`，结果完全一样。

## 三、根因定位：markPrice / resolutionPrice 被错当成 \$1.00

"按 \$1.00 估值"在代码里有两条可能的路径，两者都会产出一模一样的 347.74%。需要用一条 SQL（见第五节）确认是哪一条，但**修复方向一致**。

### 路径 A —— 持仓被提前/错误"结算"为中标

`resolvePosition()`（第 3127–3180 行）执行结算：

```
resolutionPrice    = settlementPrice(position, metadata)   // 中标=1.0，未中标=0.0
settlementProceeds = quantity × resolutionPrice
realizedDelta      = settlementProceeds − costBasisUsdc
```

`settlementPrice()`（第 3194–3227 行）只要 `marketMetadataService.isWinningPosition()` 判定为 true，就返回 `BigDecimal.ONE`（\$1.00）。而 `isWinningPosition()` 的前置条件只有 `metadata.isResolved()`，外加 `winningTokenId` / `resolvedOutcome` 的字符串比较。

风险点：

1. **`metadata.isResolved()` 对一个仍在交易的市场误判为 true** —— 一旦如此，仍在涨跌途中的持仓会被按 \$1.00 入账。
2. **`settlementAt()`（第 3187–3192 行）取的是 `metadata.getEndAt()`（市场名义到期时间），不是真实结算时刻** —— 这正是 [运行分析报告-2026-05-23] 已记录的"9 条未来时间结算"异常（`settled_at` 最远到 2026-06-30）。名义到期时间被当作结算时间，意味着结算判定与真实链上结算事件脱钩。
3. `winningTokenId` / `outcome` 标签比较一旦命中错误的 token，未中标甚至未结算的持仓也会被标为中标。

旁证：现有巡检已多次报告结算源不可靠 —— `AUDIT_SETTLEMENT_SOURCE` 告警 `delayed=819`、`smart_wallet_leader_trade_outcome` 57% 记录为 `LOW_CONFIDENCE`、9 条未来日期结算记录。结算判定链路本就处于已知不可信状态。

### 路径 B —— 未平仓持仓的 markPrice 回退到被污染的 leader 成交价

`markToMarket()`（第 3249–3264 行）取价优先级：

```
markPrice = 盘口实时价(resolveRealtimeMarkPrice)            // 首选
         → 最近一条 trade_event.price（leader 成交价）       // 盘口取不到时回退
         → position.lastMarkPrice                          // 再回退
```

代码第 3248 行注释原文："优先使用 orderbook 实时价格，**避免被 trade_event 中异常的 leader 交易价格污染**" —— 团队**已知 leader 成交价存在异常值**。但回退分支并没有对 `trade_event.price` 做任何区间校验：一旦盘口拉取失败（[报告-2026-05-23] 记录了约 48 次 API 失败 + 39 次兜底失败），就会直接采用一条可能 ≈1.0 或越界的 leader 成交价作为 markPrice，使 `unrealizedPnl` 被打到接近全额赔付。

### 共同的"看门狗"盲区

`tradeRoiAnomalyReason()`（第 4719–4740 行）本应拦截异常 ROI，但它的判据是：

```
仅当 roiRate > (1 − 入场价)/入场价 + 0.05 时才告警
```

而"按 \$1.00 估值"产生的 `roiRate` **恰好等于 `(1−p)/p`**，正好压在阈值上、不超过它，因此**永远不会被这个看门狗标记**。这是一个结构性盲区——异常检测器对这种最典型的故障完全失明。前端 `formatPercent` 也只是无脑 `× 100`，没有任何上限标注。

### 为什么排除"入场价记错"

另一种假设是入场价 `price` 被记得过低。但反推显示，要凑出 347.74% 需要入场价低到 0.128 —— 这个值**低于跟单地址的入场价 0.151**。我们是**晚于**领单地址跟进的，买入价不可能比对方更低。因此入场价记录正常（0.223），可排除该假设。错误锁定在**估值/结算用的现价**这一侧。

## 四、影响面

- **盈亏与胜率全部失真**：被错估的持仓会把 `realized`/`unrealized`/`netPnl`/`roiRate` 一起带偏；[报告-2026-05-23] 已点名"盈利主要来自少数几笔高 ROI 单（id 597 +10.09、id 598 +16.69）"——这些"高 ROI 单"极可能就是本 bug 的产物，使整体策略表现被高估。
- **策略决策被污染**：止盈/资金回收（`CapitalRecycleExitService` 用 `roiRate` 判定）、Kelly 仓位、钱包画像都会基于虚高 ROI 做出错误动作。
- **看门狗失效**：`roiAnomalyReason` 对该故障无感知，问题会静默累积。
- **两套 ROI 口径不一致**：`toTradeView` 的 `roiBase` 取"入场订单 `notionalUsdc` 之和"，`buildTradeOrder` 取"入场 fill `notionalUsdc` 之和"，二者可能不相等（代码已有 `[ORDER_UNIT_MISMATCH]` 告警佐证），同一笔持仓在不同页面可能显示不同 ROI。

## 五、确认根因走哪条路径（建议先跑这条 SQL）

定位到具体持仓（前端那笔 347.74% 的 trade），取以下字段即可一锤定音：

```sql
-- 1. 看持仓状态与估值价
SELECT id, status, quantity, average_entry_price, cost_basis_usdc,
       original_cost_basis_usdc, last_mark_price,
       realized_pnl_usdc, unrealized_pnl_usdc, closed_at, updated_at
FROM smart_wallet_position
WHERE id = <持仓ID>;

-- 2. 看聚合 trade_order 的 ROI 口径
SELECT id, status, entry_avg_price, entry_cost_usdc, roi_base_usdc,
       total_pnl_usdc, roi_rate, settlement_price, settled_at, roi_anomaly_reason
FROM smart_wallet_trade_order
WHERE position_id = <持仓ID>;
```

判读：

- 若 `status` ∈ {RESOLVED_UNCLAIMED, CLAIMED, CLOSED} 且 `settlement_price ≈ 1.0` → **路径 A（错误结算）**。再核对该 `marketId` 在 Polymarket 上是否真的已结算；若仍在交易 = 提前结算坐实。
- 若 `status = OPEN` 且 `last_mark_price ≈ 1.0`（而盘口实际 ≈0.29）→ **路径 B（markPrice 污染）**。
- `average_entry_price` 应 ≈ 0.22；若确为 0.22 则再次印证"入场价正常、估值价错"。

## 六、修复方案

### P0 —— 纠正估值/结算价（根因修复）

1. **未结算的持仓，永远不得按 \$1.00 估值。** `markToMarket()` 的 `markPrice` 必须强约束在 `[tickSize, 1 − tickSize]`（如 0.01–0.99）区间内；超出区间的取价一律丢弃。
2. **markToMarket 回退分支去污染（路径 B）。** 盘口取不到价时，不要直接采用 `trade_event.price`：
   - 对回退价做区间校验 + 跳变校验（与上一次可信 mid 偏离超过阈值即拒绝）；
   - 校验不过则**保留上一次可信 markPrice 并打 `STALE` 标记**，而不是写入一个可能 ≈1.0 的污染价。
3. **结算判定收紧（路径 A）。** `resolvePosition()` 只能在市场**真正终结**时触发：`closed && !acceptingOrders && isResolved` 三者同时成立，并以 UMA / 链上结算事件为准；`settlementAt()` 改用**真实结算时刻**，不再用 `metadata.getEndAt()`（名义到期时间）——这同时修掉"未来日期结算"的历史问题。
4. **结算前置校验。** 写入 `resolutionPrice = 1.0` 之前，加一道复核：若该市场盘口仍活跃、或当前盘口中间价与 1.0 偏离过大，则拒绝结算并告警，避免"市场还在 0.29 却按 1.0 入账"。

### P1 —— 修复看门狗盲区与口径不一致

5. **`tradeRoiAnomalyReason()` 增加"满额赔付"检测。** 当持仓**未真正结算**、但 `roiRate` 已逼近 `(1−p)/p`（即 markPrice 逼近 1.0）时，必须告警——这正是本 bug 的指纹。同时把 markPrice 与实时盘口做一次交叉校验。
6. **统一两套 ROI 口径。** `toTradeView` 与 `buildTradeOrder` 的 `roiBase` 收敛到同一个定义（建议统一用 fill 口径），消除同一持仓多页面 ROI 打架。

### P2 —— 前端展示与存量数据修正

7. **前端区分"已结算 ROI"与"浮动 ROI"**，并展示 `roiAnomalyReason`；对超过二元赔付上限的 ROI 做标注或封顶，不再无脑 `× 100`。
8. **存量数据订正：** 找出被错误结算/错误估值的持仓，重算 `realized` / `unrealized` / `roiRate`，并重建受影响的 `trade_order` 与 `daily_report`（与 [问题记录-2026-05-24] 中 P2-2「未来日期结算」一并处理）。

### 修复顺序

先做 1、2、3、4（止住继续产生虚高数据），再做 5、6（恢复看门狗与口径一致），最后 7、8（前端 + 存量订正）。建议每步配单测：构造"市场未结算但 markPrice=1.0"的用例，断言 `roiRate` 不再虚高且 `roiAnomalyReason` 被正确置位。
