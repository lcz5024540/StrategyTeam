## 问题 5：市场已结算，订单未结算（核心病灶，先修）

### 现象
38 笔 OPEN 持仓中，**17 笔所在市场本地已标记 `resolved_outcome` 非空、`market_lifecycle=RESOLVED`、`accepting_orders=0`**，最早开仓于 5/28（已超 3 天），但持仓状态仍是 OPEN，未结算、未计盈亏。

### 根因
结算作业 `SmartWalletSettlementSyncService` 每 5 分钟跑一次且**确实在工作**（CLAIMED 持仓最近一次 `closed_at` 是今天 22:55）。但结算写回路径 `SmartWalletAccountingService.classifySettlementRetryType()` 对每个市场会**重新拉取 Polymarket Gamma / UMA 在线元数据**，并要求同时满足：`isResolved()` 为真 **且** 能把「获胜结果」映射到具体 token。当：

- UMA 在线状态未最终确认（`ORACLE_PENDING` / `WAIT_FINAL_PRICE`），或
- 已 resolved 但 `closed` 标记 stale（`RESOLVED_BUT_CLOSED_FLAG_STALE`），或
- 获胜 outcome 无法映射到本地 token（`RESOLVED_OUTCOME_UNMAPPED` / `MARKET_INFO_SLUG_OR_MAPPING_ERROR`）

时，结算被推迟。问题在于：**本地 `market_info.resolved_outcome` 早已知道赢家，却没有被当作结算的兜底数据源**；而且这些卡住的持仓既没结算、也没可靠地落到 `SETTLEMENT_PENDING_ORACLE`，而是继续停在 OPEN，于是每轮重复扫描、重复失败（`settlement_retry` 里只有 1 条 PENDING，说明它们大多没进重试队列）。

### 影响链
这 17 笔卡死持仓 = ① 占着组合预算不释放（喂给问题1）② 不计入胜率分母分子（喂给问题3）。

### 修复方案
1. **兜底结算（立即见效）**：在结算路径增加一条「本地权威结算」分支——当 `market_info.resolved_outcome` 非空且 `market_end_at` 早于 N 小时（如 2h），直接用本地 resolved_outcome 判定输赢并结算（赢→1.0，输→0.0），不再强依赖在线 UMA 二次确认。保留在线确认作为优先源，本地作为超时兜底。
2. **修复 outcome→token 映射**：对 `RESOLVED_OUTCOME_UNMAPPED` 的市场，按 outcome 名称（如 "LOS ANGELES ANGELS" / "YES" / "NO"）与持仓 token 做规范化匹配（去空格、大小写、别名表）。
3. **状态收口**：凡是 `market_end_at` 已过且未能结算的 OPEN 持仓，必须落到 `SETTLEMENT_PENDING_ORACLE` 而非停留 OPEN，确保进重试队列且预算被「pending 占用」而非「OPEN 占用」可被识别。
4. **一次性清理脚本**：对当前 17 笔，按本地 resolved_outcome 批量结算（先在测试库 dry-run，核对 win/loss 笔数与 PnL 后再上生产）。

## 问题 1：长时间不开单

### 现象
5/29 之后出现断档：**5/30、5/31 两天 FOLLOWED = 0**（仅 PAPER_SHADOW / SKIPPED），6/1 才恢复（今日 FOLLOWED 12 笔）。近 7 天跳过原因里 **STALE 1918、CAPACITY 1777** 居前两位。

### 根因
1. **历史断档**：之前的根因是 `@Scheduled` 单线程调度器被重任务（闭仓同步、市场发现）饿死，导致 HOT 事件摄取滞后约 70 分钟、信号入库即过期、100% 命中 `G5_SIGNAL_STALE_INGEST`、零开单。`SchedulingConfig` 已引入 8 线程池修复，**当前摄取延迟已恢复到 ~40s**。STALE 的历史计数主要是这次事故的残留。
2. **CAPACITY 长期挤压（与问题5强相关）**：`max-total-open-cost-usdc=500`，当前已用 $330（66%）。由于问题5 的 17 笔卡死持仓**永远不释放预算**，可用额度被持续蚕食，逼近上限后所有新信号命中 `G4_MAX_TOTAL_OPEN_COST` → CAPACITY 跳过 → 表现为「长时间不开单」。这是断档的结构性原因。
3. **信号新鲜度阈值偏紧**：`max-signal-age-seconds=3600`（1 小时）。一旦摄取再次抖动，信号很快过期。

### 修复方案
1. **先修问题5**，让卡死预算回收，CAPACITY 自然缓解（最高杠杆）。
2. 监控 + 告警：对「事件摄取延迟 > 5min」「单轮 CAPACITY 跳过占比 > 50%」「连续 N 分钟 FOLLOWED=0」加 `strategy_alert`，避免再次哑火两天无人知。
3. 评估把 `max-total-open-cost-usdc` 临时上调（如 800–1000）或缩短 `capital-recycle.holding-period-hours`（当前 8h）以加快周转——**但前提是结算正常回收**，否则只是延后撞墙。
4. 复核调度线程池在生产是否真的生效（`spring.task.scheduling.pool.size`），并对高频任务做并发安全 review（见 SchedulingConfig 注释）。

## 问题 2：跟单异常，只跟了一个地址

### 现象
allowlist 有 29 个 ACTIVE 钱包，但近 3 天只有 3 个钱包产生 FOLLOWED；若按「可真实下单」口径，则只有 **1 个**地址有资格。

### 根因
1. **执行模式总开关关闭**：`auto-execution-enabled=false` → `SmartWalletFollowService` 第 107 行直接拦截所有 LIVE 跟单，全系统只能 PAPER。
2. **allowlist 执行模式几乎全是 PAPER**：`smart_wallet_manual_allowlist` 里 29 个 ACTIVE 中，**只有 `0x9d84ce…` 一个是 `BOTH`（可实盘）**，其余全是 `PAPER`。即使打开总开关，也只有这一个地址能真实跟单——这正是「只跟一个地址」的直接原因。
3. **自动 allowlist 作业只发 PAPER**：`WeeklyTopLeaderAutoAllowlistJob` 把每周 top leader 一律以 `PAPER` 加入，永远不会「毕业」到实盘，名单再长也不会增加实盘地址数。
4. **纸面跟单内部的强门控**：概率门 `min-calibrated-follow-probability=0.52`、`require-leader-profitable-active-position=true`、流动性 P30、`edge≥0.05`、CAPACITY 等叠加，进一步把通过的钱包压到个位数。

### 修复方案
1. 明确目标：若要实盘多地址跟单，需 (a) 打开 `auto-execution-enabled`（先确认 `/strategy/api/smart-wallet/execution-wallet/status` 钱包余额/授权就绪）；(b) 把经过验证的优质地址 `allowed_execution_modes` 从 PAPER 升到 `BOTH`。
2. 给 `WeeklyTopLeaderAutoAllowlistJob` 增加「晋级」逻辑：纸面表现达标（样本量 + 胜率 + PnL）的地址自动升 `BOTH`，并设单地址日限额（`max_live_orders_per_day` 已有字段）。
3. 复核 `require-leader-profitable-active-position=true` 是否过严——它要求 leader 当前持有盈利仓才跟，会大幅削减可跟地址；建议做 A/B 或放宽到「近 X 天盈利」。
4. 若当前阶段就是有意只跑纸面验证，则问题2 属预期行为，需向使用方说明，而非代码缺陷。

## 问题 3：胜率异常

### 现象
`smart_wallet_daily_report` 胜率：5/29 = **12.5%**（2 胜 / 14 负）、5/31 = **0%**（0 胜 / 6 负）、6/1 = 50%（6/6）。而被跟 leader 的标称胜率多在 **70%–100%**，严重背离。

### 根因
1. **结算偏差（主因，源自问题5）**：胜率公式 `winRate = winning/(winning+losing)`（`SmartWalletAccountingService` L1241-1243），**只统计已结算 / pending-tracked 持仓，OPEN 一律不计入**。问题5 让大量「赢面」持仓卡在 OPEN 不结算，而输的持仓往往更快确认结算 → 分母里堆满快速兑现的输单、赢单被系统性剔除 → 胜率被严重低估。5/31「0 开单却记 6 负」就是典型：当天只把输单结算了。
2. **样本极小**：单日十几笔，统计噪声大，不能代表真实胜率。
3. **次因**：跟单延迟 + 入场滑点会侵蚀边际，使实际胜率低于 leader；但量级不足以解释 12.5%。

### 修复方案
1. **先修问题5**，把卡死持仓正确结算后，**重算历史胜率**（用 `LeaderTradeOutcomeRebuildService` / 重建作业），再评估真实水平。当前胜率数字在结算修复前不可信，不应据此调策略。
2. 报表口径增强：把 OPEN/PENDING 持仓的「市场已 resolved 的隐含输赢」单列展示（已知 resolved_outcome 即可推断），避免「赢单未结算」造成的视觉低胜率。
3. 修复后若真实胜率仍显著低于 leader，再排查入场时延与滑点（对比 `entry_avg_price` vs leader 触发价、`slippageBps`）。

## 问题 4：开单/平仓必须依赖盘口，不能以现价计算

### 现象/核查结论
代码主路径**已经在用盘口**，并非完全用现价：
- **入场限价** `PolymarketOrderRequestFactory`：MAKER 取 `min(rawPrice+tickBuffer, bestBid+offset)`，TAKER 钳到 `bestAsk×(1+premium)`，均基于 best bid/ask。
- **平仓/止损监控** `PositionPriceMonitorService`：用 `book.getBids()[0]` / `book.getAsks()[0]` 做 bestBid/bestAsk 判定与挂单。
- **纸面成交** `ShadowFillSimulationService`：按 1c/3c/5c 三档深度做真分档 VWAP，基于盘口而非现价。

### 残留风险（需收口）
1. **盘口缺失时回退到「现价/leader 价」**：`PolymarketOrderRequestFactory` 在 `bestBid`、`bestAsk` 都不可用 / snapshot stale 时，回退 `rawPrice + 1 tick`，而 `rawPrice` 源自 `signal.getMarket().getPrice()`（leader/市场价，即「现价」）。这违反「必须依赖盘口」的要求。
2. **未实现盈亏 mark 价**：`last_mark_price` 若取 lastTrade/mid 而非 bestBid（多头离场应看 bid），会让止损/止盈触发基于非可成交价。

### 修复方案
1. **盘口强制门**：开单与平仓前校验盘口快照存在且新鲜（age < 阈值，如 5s）。**盘口缺失或过期时，不得用现价兜底成交——应跳过/延迟该信号**（fail-closed），并记 `G6c_ENTRY_ASK_SNAPSHOT_STALE` 一类拒绝原因（代码已有该 gate 雏形，需确保对开单/平仓双向生效）。
2. mark 价口径统一：未实现盈亏与离场判定，多头用 `bestBid`、空头用 `bestAsk`，而非 lastTrade/mid。
3. 把「盘口缺失回退现价」的分支改为「盘口缺失则不下单」，仅在明确允许的降级场景保留，且打 WARN 告警。

## 总体优先级与落地顺序

1. **P0 — 修问题5（结算回写）**：加本地 resolved_outcome 兜底结算 + 修 outcome→token 映射 + 状态收口；一次性清理 17 笔卡死持仓。**一并缓解问题1（预算回收）与问题3（胜率重算）**。
2. **P0 — 监控告警**：摄取延迟 / CAPACITY 跳过率 / FOLLOWED=0 连续时长，防止再次哑火无感。
3. **P1 — 问题4 盘口强制门**：盘口缺失/过期一律不以现价成交（fail-closed），mark 价口径统一。
4. **P1 — 问题2 实盘多地址**：确认执行钱包就绪后开 `auto-execution-enabled`，并把验证达标地址升 `BOTH` + 自动晋级逻辑。
5. **P2 — 问题1 调参**：结算修复后再评估 `max-total-open-cost-usdc` / 周转参数；复核 `require-leader-profitable-active-position` 是否过严。
6. **验证**：每项修复后用测试库 dry-run + 重算胜率 + 对账 17 笔，再灰度上生产。

> 重要提醒：在结算（问题5）修复并重算前，当前胜率、净盈亏数字均被低估，不应作为关闭/调整策略的依据。
