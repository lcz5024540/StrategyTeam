## 三、本期核心修复 1：部署 `da5ee2f0` 锁修复（P1-8，最紧迫）

### 3.1 现象（沿用 1-job 实测）

- `job-current.log` 自 **2026-05-27 07:48:57** 起，至巡检（09:38）累计 **25 次** `Lock wait timeout exceeded`，源自 `LeaderTradeOutcomeRebuildService` 对多个 wallet 的 outcome 重建。
- 与 4h 零开仓窗口（`HEALTH_NO_OPEN_4H` id=8 触发于 **08:27:48**）**时序重合**：锁等待于 07:48 开始累积，39 分钟后触发零开仓告警。
- 最后一笔真实开单 05-27 01:43:59，至巡检 ~7h55m 无新开单；今日总开单数 6 笔（全部 00:59–01:43 之间）。

### 3.2 根因（代码锚点经只读核验）

**已在 commit `da5ee2f0` 闭环。** 关键改动两处：

1. `LeaderTradeOutcomeRebuildService.java` 方法 `rebuild(walletAddress, limit)`：
   - **删除** `@Transactional`：原先把整个 wallet 循环（含 Polymarket HTTP 调用 + 每个 outcome 的 upsert）包在单事务里——HTTP 慢即整段长事务持锁，下游开仓链路碰 `smart_wallet_leader_trade_outcome` / `smart_wallet_market_info` 立刻排队 → `Lock wait timeout`。
   - 每个 outcome 的 upsert 包 try/catch：捕获 `PessimisticLockingFailureException`（覆盖 `CannotAcquireLockException` / `DeadlockLoserDataAccessException`）后只 WARN 日志、跳过该 outcome、不影响同一 wallet 其它 outcome。

2. `SmartWalletLeaderTradeOutcomeMapper.java` 新增 `upsert(entity)`：
   - **改写** 原 `selectOne → insert / updateById` 双段逻辑：MySQL REPEATABLE READ 下，SELECT 会沿唯一索引 `(wallet_address, market_id, outcome)` 占 next-key 锁；紧跟的 INSERT 又申请插入意向锁；并发 rebuild 或与开仓链路交叉时极易撞锁。
   - **改为** 单语句 `INSERT ... ON DUPLICATE KEY UPDATE`，InnoDB 一次性获取/释放行锁与间隙锁，持锁窗口压到毫秒级。

### 3.3 修复动作（已就绪 → 仅需部署）

- **代码**：✅ 已在 `da5ee2f0` 完成（`LeaderTradeOutcomeRebuildService` 改造 + `SmartWalletLeaderTradeOutcomeMapper.upsert` 新增 + `LeaderTradeOutcomeRebuildServiceTest` 已更新），无需再开发。
- **构建**：`mvn -pl coin-strategy-job -am clean package`，由 `8f9264cc` 已让 jar `MANIFEST` 注入构建 commit + 时间。
- **部署**：选开单低峰窗口（建议 02:00–06:00），通过 systemd（若 P0-2 已落地）或脚本 `systemctl stop → 备份 → 替换 → systemctl start`；部署后核对运行 jar `MANIFEST` commit = 构建 commit。
- **复测**：观察 ≥ 6h `job-current.log` `grep -c "Lock wait timeout" /opt/coinstrategy/smart-wallet/logs/job-current.log` 应明显衰减；`grep -c "Lock contention skipping outcome" job-current.log` 是新增 WARN（预期出现，但不阻塞主链路）。

## 五、本期核心修复 3：陈旧信号门治理（P0-1 / P1-7，与 P1-8 联动）

### 5.1 现象（沿用 1-job 实测）

- 今日 `firstRejectGate` 分布：`G5_SIGNAL_STALE` 1,254 次（73%）+ `G5_SIGNAL_STALE_INGEST` 95 次（6%）= **合计 79%**（上版 36%）。
- `SKIPPED` 任务 `primary_skip_reason`：`STALE` 97（92%）。
- `trade_event` 近 4h 摄取 AVG=580s、MAX=896s（**接近** 600s WARN 阈值，但远低于 3,600s 硬新鲜度上限）——说明大量信号被拒**并非因为摄取延迟**，而是「信号本身在源端就已陈旧」或「`resolveEffectiveSignalAgeMs` 在 archetype 上更严」或「P1-8 锁阻塞 → follow-task 处理被延迟 → 信号在等待期间过期」三者之一/组合。

### 5.2 根因（代码锚点经只读核验）

- 入口判定在 `SmartWalletSignalRiskService.java:397-415`：
  ```java
  if (event.getOpenedAt() != null) {
      long ageMs = Math.max(0L, System.currentTimeMillis() - event.getOpenedAt().getTime());
      long effectiveMaxSignalAgeMs = resolveEffectiveSignalAgeMs(risk, archetype);
      if (ageMs > effectiveMaxSignalAgeMs) {
          long paperCanaryMaxAgeMs = defaultInt(risk.getPaperCanaryMaxSignalAgeSeconds(), 0) * 1000L;
          if (paperCanaryAdmissionCandidate && paperCanaryMaxAgeMs > 0 && ageMs <= paperCanaryMaxAgeMs) {
              paperCanaryGateSoftened = true;
              // ... paper canary 软降级
          } else {
              accepted = false;
              if (firstRejectGate == null) firstRejectGate = "G5_SIGNAL_STALE(age=...s,max=...s)";
              reasons.add("Signal is stale for lane " + archetype.followLane() + ".");
          }
      }
  }
  ```
  - 关键点 1：**判定基于 `event.getOpenedAt()`**——而非 `event.getCreatedAt()` / `ingest_at`；如果 leader 在链上成交后到 trade_event 入库存在 ≥ 数百秒延迟，开仓时 `ageMs` 已经接近 `effectiveMaxSignalAgeMs`，**只要再叠加一个锁等待 (P1-8) 让 follow-task 多排队 60 秒，就会被拒**。
  - 关键点 2：**`resolveEffectiveSignalAgeMs(risk, archetype)`** 允许按 archetype 差异化阈值——需要查 `strategy_runtime_config` 中是否有 archetype 覆盖把某些 lane 拉得更严。
  - 关键点 3：**`paperCanaryMaxSignalAgeSeconds` 软降级口径已存在**——若启用并放宽到 `2 * max-signal-age-seconds`，可显著降低 G5_STALE 拒单。
- `G5_SIGNAL_STALE_INGEST` 在 `SmartWalletFollowTaskService.java:901` 触发——是入口前另一道闸（在风控前的 follow-task 同步阶段就拒）。

### 5.3 修复动作（**依赖 P1-8 部署完成 + 24h 观察**）

1. **第一步：先排除 P1-8 锁干扰**。`da5ee2f0` 部署后观察 24h `firstRejectGate=G5_SIGNAL_STALE*` 占比是否回落；若回落到 ≤ 40%，说明根因主要是锁阻塞，无需调闸门。
2. **第二步（若 G5 占比仍 ≥ 50%）：核对 `resolveEffectiveSignalAgeMs` archetype 覆盖**：
   ```sql
   SELECT config_key, config_value, lane_archetype FROM strategy_runtime_config
   WHERE config_key LIKE '%signal-age%';
   ```
   - 若发现某 lane 阈值 < 全局默认 3600s，评估是否过严。
3. **第三步：缩短 HOT 钱包同步轮询**：在 `coin-strategy-job` 找 HOT 钱包 `@Scheduled`（候选 `SmartWalletEventSyncJob` 或类似），从当前轮询间隔降到一半；评估 Polymarket 端限流。
4. **第四步：试启用 `paperCanaryMaxSignalAgeSeconds` 软降级**：在 `strategy_runtime_config` 设 `smart-wallet.signal-risk.paper-canary-max-signal-age-seconds = 7200`（= 2 × 3600），观察 paper canary lane 的 follow-up 转化率。
5. **第五步：HEALTH_INGEST_LAG_HIGH 自愈核查**：完成上述后，id=6 应被 `autoResolveByStrategy` 关闭（`1ed101bc` 已部署）；若仍未 resolved，复查 `TradeEventIngestLagService` 的阈值与 dedupe 窗口。

### 5.4 风险与回滚

- 缩短轮询会增 Polymarket API 调用量——观察 24h 是否触发限流；如触发回退原间隔。
- `paperCanaryMaxSignalAgeSeconds` 放宽属于「软降级」，仅放过 paper canary lane，对真实仓位无影响——风险可控。
- archetype 阈值若调整后 G5 占比未变但出现新「低质量信号入场后亏损」——需配合 P1-1 allowlist 收紧抵消。
