## 三、五大根因（按贡献排序）

> 按 `troubleshooting` 技能的"现象 → 证据 → 根因 → 影响 → 状态 / 建议"结构记录。

### 根因 #1 ★ 无止损路径直接把损失锁死为 -100%

- **现象**：13 笔损单全部 ROI 精确 = -1.0（全损），没有任何中途减仓或止损动作。
- **证据**：
  - `smart_wallet_order` 24h `side`：BUY 88 / **SELL 0**
  - `smart_wallet_order.exit_reason`：**全表 0 行非空**
  - `smart_wallet_trade_order` 7d SETTLED 15 笔：`last_exit_at` 100% NULL、`exit_avg_price` 100% = 0
  - `grep -ac 'CAPITAL_RECYCLE' job-current.log` → **0**
  - 配置：`signal-risk.capital-recycle.paper-enabled` / `position-price-monitor.auto-exit-enabled` 两个 PAPER 入口开关 DB 未配置 → 代码默认 `false` → 全部路径短路。
- **根因**：`SmartWalletProperties.CapitalRecycle.paperEnabled=false`（默认）+ `PositionPriceMonitor.autoExitEnabled=false`（默认），且 DB 未覆盖。`CapitalRecycleExitService.checkCapitalRecycle()` 直接跳过 PAPER 扫描；`liveEnabled=true` 又因 `auto-execution-enabled=false` 在 PAPER 模式下取不到 LIVE wallet context 立即 return。三套止损服务都成 dead code。
- **影响（量化）**：把损单的 ROI 从"假设按 -35% stop-loss 触发"的 -0.35 抬到了实测的 -1.00。13 笔损单 cost 153.94 USDC，若全部按 -35% 止损平仓：
  ```
  假设止损后回收 = cost × (1 − 0.35) = 153.94 × 0.65 = 100.06 USDC
  对应损失     = -(153.94 − 100.06) = -53.88 USDC
  当前实际损失  = -153.94 USDC
  止损可挽回    = 153.94 − 53.88 = 100.06 USDC ≈ 119% × |当前 net|
  ```
  **结论：仅这一项修复，期望就能把 net PnL 从 -84 翻正到约 +16 USDC（按 2W/13L 不变假设）。**
- **状态 / 建议**：见 [问题记录事项-待解决-2026-05-29] §3.4-E2 三条 SQL（已草拟，待评审执行）。

### 根因 #2 ★ 单钱包 `0x2005…875ea` 独占 86% 损失，且自身长期负期望

- **现象**：该钱包贡献了 10/15 settled 笔（cost 146.14、net -86.73），其 leader_trade_outcome 历史胜率仅 44.6%、期望 ROI ≈ -0.32。
- **证据**：
  - 7d settled 按钱包归因表（§2.2）：单笔最大损 -86.73，其余三家合计 +2.72；
  - `smart_wallet_leader_trade_outcome` 全表（§2.3）：25 CLOSED_WIN + 31 CLOSED_LOSS，期望式 -31.6%；
  - 当前 OPEN 占 10/49 笔、cost 62.49 USDC（同时是 P0-3 提到的 #1 集中钱包）；
  - 在 `manual_allowlist` ACTIVE 列表中（详 P1-3 反弹 27 条）。
- **根因**：(a) 这条钱包习惯押中低概率事件（中低 entry price 区间被它垄断），与 §2.5 "0.20-0.30 桶全损 -71.11" 强相关；(b) 没有"加入 → 观察 → 评分 → 自动剔除"的 allowlist 闭环；(c) Kelly 模型把它的 follow probability 估到 0.7667（取自 §3.1 日志），与实测 0.143 偏差 5x，提示模型严重高估。
- **影响（量化）**：在不动其他变量的前提下，**仅移除该钱包带来的影响 = +86.73 USDC**，能让 7d net 从 -84.01 翻为 +2.72。
- **状态 / 建议**：今日内做三件事：
  1. `UPDATE smart_wallet_manual_allowlist SET status='DISABLED' WHERE LOWER(wallet_address)='0x2005d16a84ceefa912d4e380cd32e7ff827875ea'`（先停加新单）；
  2. 主动清掉该钱包当前 10 笔 OPEN 仓位（cost 62.49 USDC）——配合根因 #1 修复后由 capital-recycle 自动触发；
  3. 落地 `max-single-wallet-open-ratio = 25%` 硬限（[问题记录事项-待解决-2026-05-28] P0-3 已建议未落地）。

### 根因 #3 SPORTS 品类结构性不适合"无止损跟单 + 等到期"

- **现象**：14/15 settled、35/49 OPEN 都在 SPORTS；Counter-Strike Map Winner、足球 BTTS、O/U 比分类是核心子类。
- **证据**：§2.4 品类分桶表；SPORTS 类目 ROI 平均 ~-0.5，唯一非负子类是 Map 2 Winner（1W/1L）。
- **根因**：SPORTS 比赛常常 30 分钟–2 小时内 winner-take-all 结算，留给"中段反弹"的窗口极短；在没有止损的情况下，这类品种的 ROI 分布天然向 ±1 两极移动；而 Polymarket 上 leader 钱包大多是带有"内幕信息"的 directional traders，本策略**滞后跟单 + 等到期**的模型在这类品种下被双向收割：（a）leader 真盈利的票，本策略也能跟到；（b）leader 亏损的票，本策略全损跟到底。
- **影响（量化）**：若移除 SPORTS Match Winner + BTTS 两个子类（合计 8 笔 1W/7L 净 -81.27 USDC），7d net 几乎归零。但样本只有 15 笔不足以下定论。
- **状态 / 建议**：(a) 短期：在 `strategy_runtime_config` 增加 `smart-wallet.signal-risk.enabled-categories = POLITICS,CURRENT_EVENTS,MACRO,CRYPTO`（暂时停 SPORTS）；(b) 中期：按品类分桶训练 Kelly 模型，SPORTS 单独评估 follow probability 与 stake 比例。

### 根因 #4 跟单底层数据 `LOW_CONFIDENCE` 45.3% — 弱化 9 道风控门判断

- **现象**：`smart_wallet_leader_trade_outcome` 共 144,269 行，`LOW_CONFIDENCE` 65,375（45.3%）；`0x2005` 单钱包 1,138 行 outcome 中 LOW_CONFIDENCE 占 1,009（88.7%）。
- **证据**：[问题记录事项-待解决-2026-05-28] §P2-4 + 本期 §2.3。
- **根因**：rebuild 在补历史 outcome，但其中近一半样本本身就被打了"低可信度"标签，Kelly / 信号风控模型却仍把它们当作有效观测。
- **影响**：Kelly 模型 follow probability 估计严重偏离实测（0.77 vs 0.14），间接放大根因 #2 的钱包选错风险。
- **状态 / 建议**：按 [问题记录事项-待解决-2026-05-28] P2-4 推进 rebuild 完成后归档 `LOW_CONFIDENCE` 行；模型训练时排除该标签。

### 根因 #5 入口 STALE 门拒了 57% 新鲜信号 — 进场时机偏向"尾段"

- **现象**：今日 `firstRejectGate` 中 `G5_SIGNAL_STALE_INGEST` 331 + `G5_SIGNAL_STALE` 138 = 469 / 820 ≈ 57%；事件摄取 P90 时延 894s。
- **证据**：[问题记录事项-待解决-2026-05-29] §3.3 + `HEALTH_INGEST_LAG_HIGH` 告警 id=2 未恢复。
- **根因**：HOT 钱包同步轮询稳态时延 + 上游回填风暴叠加，导致策略**只能跟到"事件已发生 ≥ 10 分钟"之后的信号**——而 Polymarket 上的"早进场红利"在前 5 分钟就被吃掉。
- **影响（间接）**：表现为 entry price 偏高、follow probability 校准偏差。难以量化但与 §2.5 "0.30–0.40 桶赢、低价桶全损"现象一致：策略在"价格已经动起来"的位置进场，没有获得"早进场便宜价"的安全边际。
- **状态 / 建议**：见 [问题记录事项-待解决-2026-05-29] §P1-1 / §P1-4（缩短 HOT 钱包轮询 / 改 push / 回填数据分流）。

## 五、注意事项与延伸

1. **样本量小（15 笔）的统计不稳定性**：根因 #3（SPORTS 品类）与根因 #5（进场时机）的量化贡献需要更大样本才能稳定。建议在落地动作 1+2 后**至少累积 100 笔 SETTLED 再回评**，避免被前期小样本误导。
2. **"赢单 ROI ≥ +1.5、损单 ROI = -1.0" 是 PAPER 模式的特征**：LIVE 模式下加入手续费 / 滑点后，赢单 ROI 会被压缩到 +0.7~+1.0，损单 ROI 仍是 -1.0（无止损时）。当前 PAPER 数据**高估了胜单收益、低估了亏损扩张**——LIVE 上线前必须先把根因 #1 与 #2 处理完。
3. **关于 "leader 钱包真实胜率 44.6% 但本策略只复制到 14.3%"**：差距过大有两种可能——
   - 模型选错跟单时机（根因 #5 + #4）；
   - 模型选错跟单事件（leader 同时操作多个 outcome，本策略只跟了输的那一面）。
   建议落地 §六 中的"跟单事件对照表" 排查。
4. **本期亏损"看起来"很高（-84 / -62%）**：但绝对金额仅 -84 USDC、cost 192 USDC。**真正的风险是趋势** —— 如果根因 #1 与 #2 不修，LIVE 上线后这套结构会按相同比例放大到 -8400 USDC / cost 19,200 USDC 的量级。

## 七、附录 A — 复现脚本与查询

> 本文所有数字均可由如下 SQL 在 test 库 `coin_strategy` 直接复现（仅 `SELECT`，无写操作）。

### A.1 总览（§2.1）

```sql
SELECT COUNT(*) total,
       SUM(total_pnl_usdc > 0)               wins,
       SUM(total_pnl_usdc < 0)               losses,
       SUM(ABS(roi_rate + 1) < 0.01)         full_losses,
       SUM(roi_rate > 1)                     big_wins,
       ROUND(SUM(total_pnl_usdc),   2)       net_pnl,
       ROUND(SUM(entry_cost_usdc),  2)       cost,
       ROUND(AVG(roi_rate),         4)       avg_roi
  FROM smart_wallet_trade_order
 WHERE status = 'SETTLED'
   AND settled_at >= NOW() - INTERVAL 7 DAY;
```

### A.2 按 leader 钱包归因（§2.2）

```sql
SELECT ft.wallet_address                                  wallet,
       COUNT(DISTINCT t.id)                               trades,
       SUM(CASE WHEN t.total_pnl_usdc > 0 THEN 1 ELSE 0 END) wins,
       SUM(CASE WHEN t.total_pnl_usdc < 0 THEN 1 ELSE 0 END) losses,
       ROUND(SUM(t.entry_cost_usdc), 2)                   cost,
       ROUND(SUM(t.total_pnl_usdc),  2)                   net_pnl
  FROM smart_wallet_trade_order  t
  JOIN smart_wallet_follow_task  ft ON ft.id = t.source_follow_task_id
 WHERE t.status = 'SETTLED'
   AND t.settled_at >= NOW() - INTERVAL 7 DAY
 GROUP BY ft.wallet_address
 ORDER BY net_pnl ASC;
```

### A.3 `0x2005` 钱包 leader outcome 统计（§2.3）

```sql
SELECT outcome_status,
       COUNT(*)                              cnt,
       ROUND(AVG(estimated_roi_rate), 3)     avg_roi,
       SUM(is_win)                           wins
  FROM smart_wallet_leader_trade_outcome
 WHERE LOWER(wallet_address) = '0x2005d16a84ceefa912d4e380cd32e7ff827875ea'
 GROUP BY outcome_status
 ORDER BY cnt DESC;
```

### A.4 当前 OPEN 浮亏分布（§2.7）

```sql
SELECT CASE
         WHEN unrealized_pnl_usdc / NULLIF(cost_basis_usdc, 0) <= -0.50 THEN '5: <=-50%'
         WHEN unrealized_pnl_usdc / NULLIF(cost_basis_usdc, 0) <= -0.30 THEN '4: -50%~-30%'
         WHEN unrealized_pnl_usdc / NULLIF(cost_basis_usdc, 0) <= -0.10 THEN '3: -30%~-10%'
         WHEN unrealized_pnl_usdc / NULLIF(cost_basis_usdc, 0) <  0     THEN '2: -10%~0%'
         ELSE '1: >=0%'
       END                                  dd_bucket,
       COUNT(*)                             cnt,
       ROUND(SUM(cost_basis_usdc),   2)     cost,
       ROUND(SUM(unrealized_pnl_usdc), 2)   upnl
  FROM smart_wallet_position
 WHERE status = 'OPEN'
 GROUP BY dd_bucket
 ORDER BY dd_bucket;
```
