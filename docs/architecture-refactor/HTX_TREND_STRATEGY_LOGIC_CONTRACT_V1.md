# HTX 趋势策略逻辑合同 v1

## 目的

Python 不是 Java 的逐行翻译，也不以同一根 K 线必须生成同一笔订单为验收目标。两种运行时可能因为盘口、手续费档案、账户仓位、信号时效和市场状态不同而产生不同的执行结果。

迁移的硬要求是：Python 必须覆盖完整的趋势策略语义，不能只迁移 EMA、Fibonacci 或一个简化 gate 后就宣称可替换实盘。每个开仓、持仓和退出决定都必须能回答“哪个模型、为什么在此刻、以什么价格、承担多少风险、何时撤销该判断”。

Java 当前实现是已有生产行为的证据来源；Python 的目标是一个更清晰、模块化、可独立部署的策略运行时。Python 完成切换后，Java 不再是同账户同策略的并行决策者。

## 完整策略闭环

```mermaid
flowchart LR
  A[市场数据与账户事实] --> B[市场状态与多周期上下文]
  B --> C[独立模型并行生成候选]
  C --> D[模型路由与候选排序]
  D --> E[开仓 Gate]
  E --> F[价格计划与仓位风险预算]
  F --> G[订单执行与对账]
  G --> H[持仓趋势再评估]
  H --> I[利润保护、减仓、退出]
  I --> J[账本、归因、回放和策略质量]
  J --> B
```

## 合同一：输入与事实边界

- 只使用已收盘 K 线；每个周期都保留 bar 时间、来源、连续性和内容 hash。
- 入场用 `15min/30min`，方向确认用 `1h/4h`，大环境用 `1d`；不是将所有周期混成一个均值。
- 盘口、深度、实际账户费率、资金费、合约精度、保证金、开放挂单、交易所仓位均是执行事实，不是技术指标。
- 当前策略账户、镜像账户、人工外部仓位必须有不同身份，不能混算。

## 合同二：市场状态

Python 必须先输出当前市场状态，而不是直接让单币种指标下单：

- 宽度：普涨、普跌、混合、震荡；使用合约横截面的方向比例与质量。
- 锚点：BTC、ETH 的 `15m/30m/1h/4h` 多周期状态。
- 波动：正常、低波动、异常扩张；异常扩张影响执行方式和仓位，而不是把所有信号一律丢弃。
- 交易质量：候选自身的趋势质量，禁止用最近几笔交易输赢冒充本次候选质量。

市场状态用于候选排序、逆市场准入、仓位倍率、保护价宽度；它不能凭空把无结构的弱信号提升为开仓信号。

## 合同三：模型并行与路由

同一批已收盘 K 线应并行计算模型，不把“一根 K 线归属一个模型”。每个模型保留独立入场、失效和目标假设：

| 模型 | 适用阶段 | 入场结构 | 主要风险 |
|---|---|---|---|
| Donchian / 箱体突破 | 趋势启动 | 收盘突破边界且多周期同向 | 假突破、插针、追价 |
| Fibonacci 回踩延续 | 已有趋势的第二段 | 先有独立突破，再进入回撤带并重获结构 | 旧结构复用、影线假回踩、延续衰竭 |
| EMA/VWAP 动量延续 | 趋势加速或浅回踩 | EMA 堆叠、ROC、VWAP 与量能同向 | 高位追涨、动量背离 |
| 市场广度驱动 | 全市场共振 | 多币种和 BTC/ETH 同向，作为增强证据 | 忽略独立行情 |

模型路由器选择**主模型**，并将其他模型标为确认、冲突或风险证据。路由不是固定优先级：根据市场状态、模型自身结构质量、剩余风险收益和执行可行性排序。每次新交易都创建新的结构身份；上一笔同币种交易不能让下一笔沿用旧突破或旧失效价。

## 合同四：开仓 Gate

Gate 的顺序应使便宜、确定的判断靠前，账户和交易所查询靠后：

1. 运行模式、策略实例、账户授权、同实例互斥。
2. K 线完整性、信号时效、周期画像和模型结构是否完整。
3. 市场状态、候选趋势状态、方向置信和逆市场资格。
4. 冷却、同结构占用、已有策略挂单、人工外部仓位、账本与交易所不一致。
5. 盘口点差、可执行深度、异常波动、追价、实际费率与资金费。
6. 目标价格、失效价格、最差可成交价格下的扣费后预期收益。
7. 策略额度、账户总额度、并发仓位、保证金、杠杆和风险预留。

每个失败 gate 必须写明阶段、输入和原因。`OBSERVE` 只能记录前四类候选与诊断；它不能伪装为“真实 gate 已通过”。

## 合同五：价格、订单与仓位

- 候选输出理想入场价、最差可接受价、失效价、第一结构目标、runner 目标和有效期。
- 订单方式由模型和盘口决定：突破可条件/IOC/市价；回踩可限价探路；不以“永远市价”或“永远限价”为规则。
- 仓位取最小值：模型失效风险预算、策略额度、账户总预留额度、交易所可用保证金和流动性上限。
- 下单前先写仓位与订单 intent、再预留账户风险、再发交易所请求；拒单、部分成交、超时、重启都须可恢复与对账。
- 镜像账户只跟随主账户已成交量，不因主账户意图或候选而抢先下单。

## 合同六：持仓趋势与退出

持仓后不使用开仓时的固定分数。每次管理至少更新：入场周期状态、`1h/4h/1d` 方向、结构是否仍完整、MFE/MAE、成本后的当前净收益、保护价和剩余目标收益。

退出优先级固定为：

1. 交易所/账本异常和硬风险；
2. 初始失效、模型结构破坏；
3. 已武装利润保护被有效穿越；
4. 趋势仍强则保持 runner 并更新保护价；
5. 有利润但预期净收益恶化时动态减仓；
6. 结构、动量、市场状态至少两类反转证据确认时全平；
7. 资金费成本和时间价值只作为经济性证据，不能覆盖硬失效。

当前版本名固定为 v4；任何新退出理论必须在新的实验模块中验证，未经用户明确决定不得改名或替换 v4。

## 合同七：账本、归因与评价

- 订单、成交、费用、资金费、已实现和未实现收益分别记录；不能用最后一笔订单或浮盈重算历史收益。
- 每个仓位、订单、退出决定、K 线输入和模型结构均关联 `run_id`、账户、策略实例和因子快照。
- 归因至少区分：方向错误、结构错误、执行价格错误、过早退出、过晚退出、成本侵蚀、交易所/账本故障。
- 回测、纸面和实盘使用同一策略合同，但执行成本、成交假设和资金账户数据各自明确标注。

### 2026-10-08 一致性实现记录

Python 已不再使用“`evaluate_signal()` 的单一方向结果决定是否生成候选”的旧路径。新的 `model_candidates()` 对 Donchian、Fibonacci、EMA/VWAP 同时分析同一批完成 K 线；`route_candidates()` 再将其中一个候选选作本轮主执行假设。其他候选仍保留为确认或冲突证据，不能被主模型覆盖。

新 `ExecutionFacts` 是 Python 连接真实执行前的硬边界：账户真实费率、多档可成交深度、开放订单、外部仓位、保证金、杠杆和账户风险预留必须由适配器显式提供。纸面和研究运行可以记录“未评估”，严格模式不能把缺失事实误当通过。此改动未启用任何真实订单，也不改变 Java 服务。

## 验收方式

不采用“每根 K 线必须下同一单”的验收。采用以下语义验收：

1. 每一个合同模块都有输入、输出、失败原因和状态持久化测试。
2. 对固定市场快照，Python 能完整输出模型、主模型、价格计划、每个 gate、风险预算和行动，而不是只给出一个分数。
3. Java 历史样本仅用于检查 Python 是否遗漏策略场景，例如外部仓位、假突破、Fibonacci 回踩、强趋势 runner；结果不同必须能解释为输入事实或策略版本差异。
4. Python 纸面运行先证明账本、费用、部分成交、重启恢复和镜像一致，再决定 live 灰度。

### Java / Python 开仓一致性约束（2026-10-08）

真实执行时，Python 必须把数据库政策选择作为模型路由的最后授权：候选的主模型和确认模型字符串必须精确命中启用政策，且候选**原始分数**达到政策阈值。市场广度和 BTC/ETH 只可修改候选排序及仓位倍率，不能以加分绕过政策准入。

Python 下单也必须保留 Java 当前的事实顺序：读取五档盘口、实际账户费率、开放委托、交易所仓位、保证金与风险预留后，使用方向盘口价格评估追价和扣费后 R；只有通过这些 gate 才可切杠杆、写入仓位/订单 intent、预留风险并发送 V5 市价单。交易所 `state` 是对账主字段，legacy 数字 `status` 仅为兼容回退；不能由本地仓位或订单接受响应推定成交。
