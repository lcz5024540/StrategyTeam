# Polymarket 跟单策略 — 定时任务调度分析与整改方案

> 生成日期：2026-05-24
> 范围：`coin-strategy-job` 模块 `smartwallet` 包下全部 `@Scheduled` 任务
> 目的：梳理任务清单与时间间隔，识别调度冲突，定义主线/次要任务分层，并给出整改方案设计

---

## 1. 概述

Polymarket 跟单策略（`smartwallet` 包）当前共有 **51 个 `@Scheduled` 定时方法**，覆盖从信号摄取、下单决策、订单/仓位同步，到画像快照、审计对账、离线报表的全链路。

整个 `coin-strategy-job` 模块（含 weather / engine / grid / btcminute 等其它策略）合计 **79 个 `@Scheduled` 方法**，全部共用同一个全局调度线程池。这是后续所有冲突分析的前提。

核心结论提前：

- 调度线程池只有 **8 条线程**，却要承载 79 个定时任务，热路径（秒级交易闭环）与重型后台任务（分钟级 API/DB 密集任务）**共用同一线程池**，存在热路径被饿死的结构性风险。
- 大量任务以 **5 分钟（300000ms）** 为节拍，相位一旦对齐会出现瞬时聚簇。
- 多个 cron 任务在整点重叠，其中 **周一 06:00 三任务同时触发**。
- 所有任务都直连 Polymarket 三个 REST API（data / gamma / clob），**没有全局限流器**，仅有单次调用级的 429 退避重试。
- 多个快照/维护任务并发写入 `smart_wallet_profile` 同一批行，多线程化后存在并发写风险。

## 2. 调度基础设施现状

调度器由 `coin-strategy-job/.../config/SchedulingConfig.java` 定义：

| 项 | 现状 |
|---|---|
| 调度器类型 | `ThreadPoolTaskScheduler`（全局唯一 Bean `taskScheduler`） |
| 线程池大小 | **8**（`DEFAULT_POOL_SIZE`，可由 `spring.task.scheduling.pool.size` 覆盖，当前配置文件未覆盖） |
| 线程名前缀 | `sched-` |
| 覆盖范围 | 全模块 79 个 `@Scheduled` 方法共用此池（含 weather / engine / grid / btcminute） |
| 同方法重入 | Spring 保证单个 `fixedDelay` 任务不会自我并发重入；不同任务之间可并行 |
| 分布式锁 | **无**（无 ShedLock / Redis 锁），隐含"单实例部署"假设 |

关键背景：该类的 Javadoc 已记录历史故障 —— 早期 Spring 默认单线程调度器导致重任务占满唯一线程、30s 的 HOT 事件同步被饿死、信号摄取滞后约 70 分钟、100% 命中 `G5_SIGNAL_STALE_INGEST`、零开单。引入 8 线程池缓解了该问题，但**并未根治**：8 线程对 79 个任务仍是紧约束，且 Javadoc 自身明确提示"多线程化后若不同任务共享可变状态可能出现并发问题，上线前需 review"。

补充：闭仓同步另有独立线程池 `smartWalletClosedSyncExecutor`（core=1 / max=2 / queue=200，HTTP 并发由 Semaphore 限 4）。因此 `ClosedPositionIncrementalSyncJob` / `ClosedPositionFullResyncJob` 的 `@Scheduled` 方法本身只做"派发"，重活在独立池跑，对 `sched-` 池占用较轻——这是现状中唯一已做隔离的部分。

## 4. 冲突与风险分析

### 风险 1 — 线程池争用：热路径被重型任务饿死【高危】

**机制**：8 条 `sched-` 线程被 79 个任务共用。热路径（任务 1–6）以 2–15s 节拍频繁要线程；而重型任务——`scheduledDiscoverWallets`（1h，API 密集，单次可达数分钟）、`refreshAllEntitySnapshots`（6h，遍历全实体）、各类 snapshot 任务（DB 密集）、`refreshLeaderboardWatchlist`、weather/engine 模块任务——单次运行时间长。

只要某一时刻有 8 个中/重型任务同时占满 8 条线程，**接下来这段时间内 2s 的订单轮询、撤单扫描就拿不到线程**：成交检测延迟 → maker 超时撤单延迟 → 卡单堆积 → 追价失效 → 错过跟单时机。这正是 `SchedulingConfig` Javadoc 记录过的故障模式，8 线程只是把触发概率降低，没有消除。

**判断**：⚠️ 会发生冲突。属于结构性风险，热路径与后台任务必须做线程池隔离。

### 风险 2 — 5 分钟节拍相位聚簇【中危】

第 3.2 节中**约 10 个任务**生效间隔恰为 5min（任务 17–26），另有多个 10/15/30min 任务是 5min 的整数倍。`fixedDelay` 从"上次完成"计时，长期会自然错相；但在以下情况会瞬时对齐：

- 应用启动瞬间：约 70 个 fixedDelay 任务 t=0 同时就绪，8 线程只能跑 8 个，其余排队——启动期热路径必然被推迟（瞬时但确定发生）。
- 多个任务耗时相近时，完成时刻趋同，再次同相位触发，形成周期性聚簇。

**判断**：⚠️ 启动期必然发生；运行期为概率性瞬时聚簇。需用 `initialDelay` 错相 + 线程池隔离共同缓解。

### 风险 3 — Cron 整点碰撞【中危】

`SettlementSourceAuditJob` 每小时整点触发，与其它整点 cron 精确重叠：

| 时刻 | 同时触发的任务 |
|---|---|
| 每日 02:00 | 结算来源审计 + 实盘回放差异（`LiveReplayDiffJob`） |
| 每日 06:00 | 结算来源审计 + Top leader 自动白名单 |
| **每周一 06:00** | 结算来源审计 + Top leader 自动白名单 + **影子周报**（三任务并发） |
| 每日 08:00 | 结算来源审计 + leader 漂移聚合 |

这些都在凌晨/清晨低峰期，线程数层面 8 线程能容纳；但它们会**同时冲击数据库与 Polymarket API**。周一 06:00 的三任务齐发最值得关注。

**判断**：⚠️ 确定性碰撞，影响可控但应错峰。

### 风险 4 — Polymarket API 无全局限流【中高危】

所有任务直连 `data-api` / `gamma-api` / `clob` 三个 REST 端点。`PolymarketApiClient` 仅有**单次调用级**的 429/5xx 退避重试（`sleepQuietly(attempt*300ms)`），**没有跨任务的全局令牌桶/限流器**。

事件同步（30s）、仓位同步（15s）、市场快照（45s）、市场缓存刷新（60s）、发现/排行榜/WARM 指标、闭仓同步等任意时刻可能并发打 API。多线程化后并发度更高，触发 429 的概率随之上升；而 429 后各任务**各自独立退避**，缺乏协调，可能形成"集体退避→集体重试"的抖动。

**判断**：⚠️ 高并发窗口会冲突。建议引入全局限流器。

### 风险 5 — 共享表并发写入【中危】

多个任务并发写同一批 `smart_wallet_profile` 行：`refreshLeaderTruthAndProfiles`、`refreshInternalWinRate`、`applyActivityDecay`、`BehaviorProfileSnapshotJob`、`ProfileOrderStatsSnapshotJob`、`ProfileDiagnosisSnapshotJob` 等。单线程时代它们隐式串行，多线程化后可真并行。

`SchedulingConfig` Javadoc 已明确点名该风险（"若不同任务共享可变状态可能出现并发问题"）。后果是行锁等待、潜在死锁、或快照读到半更新状态。

**判断**：⚠️ 存在并发写风险，需串行化或加锁。

### 风险 6 — 无分布式锁，多实例会重复执行【部署约束】

无 ShedLock/Redis 锁。一旦 `coin-strategy-job` 扩到 2 个及以上实例，**每个定时任务会在每个实例各跑一次**——重复下单、重复领奖、重复审计。当前隐含"单实例"假设。

**判断**：⚠️ 单实例下无影响；属于横向扩容前必须先解决的前置约束。

## 5. 主线任务 vs 次要任务分层定义

按"是否处在跟单交易闭环关键路径上、对延迟是否敏感"划分为三层。**主线 = Tier 1**；**次要 = Tier 2 + Tier 3**（Tier 2 为"次要但需保持较新"，Tier 3 为"可延迟/可错峰的观测与离线任务"）。

### Tier 1 — 主线任务（交易闭环热路径，绝不可被饿死）

直接决定"能否跟上单、跟单快慢、能否及时止损止盈"的任务。延迟会直接造成漏单、卡单、风控失效。

| 任务 | 间隔 | 在闭环中的位置 |
|---|---|---|
| `scheduledSyncWatchlistTrades` | 30s | 信号摄取入口 |
| `processPendingTasks` | 5s | 核心下单决策 |
| `pollPendingOrders` | 2s | 订单成交状态 |
| `MakerOnlyOrderTimeoutTracker.scan` | 2s | 卡单撤单 |
| `GtcOrderTimeoutTracker.scan` | 3s | 卡单撤单 |
| `MakerPriceFollowupService.scan` | 3s | 挂单追价（决定成交率） |
| `syncPositions` | 15s | 持仓/余额真值 |
| `checkStopLoss` / `checkTakeProfit` | 5min | 风控退出 |
| `CapitalRecycleExitService.checkCapitalRecycle` | 5min | 资金回收退出 |
| `refreshActiveMarkets` | 60s | 下单依赖的市场数据 |
| `PolymarketWatchlistSubscriptionService.refreshSubscriptions` | 60s | 行情订阅维持 |

共 **12 个**。这一层必须保证每个调度周期都能即时拿到线程。

### Tier 2 — 支撑任务（次要，但需保持较新）

热路径会读取其产出，但容忍数分钟级陈旧。延迟不会立刻漏单，但长期滞后会降低决策质量。

`drainStaleSignalBacklog`(2min)、`scheduledReevaluateDeferredCandidates`(2min)、`expireStalePendingTasks`(5min)、`MarketConcentrationMonitorJob.scanOpenPositions`(5min)、`MarketConcentrationSnapshotRefreshJob`(3min)、`MarketMetadataRefreshJob`(5min)、`MarketInfoEndAtRefreshJob`(10min)、`SmartWalletLeaderTruthMaintenanceJob`(15min)、`refreshInternalWinRate`(15min)、`SmartWalletClaimService`(60s)、`SmartWalletSettlementSyncService`(5min)、`SmartWalletLiveValidationService`(45s)、`evictStaleOrderBooks`(5min)。

共约 **13 个**。

### Tier 3 — 次要任务（观测、画像、离线分析与对账）

不参与实时交易决策，可延迟、可错峰、可批量化、可移到低峰期。

发现类：`scheduledDiscoverWallets`(1h)、`scheduledRefreshLeaderboardWatchlist`(30min)、`scheduledRefreshWarmWalletMetrics`(10min)、`WalletEntityIntelligenceJob`(1h)、`EntityFeatureSnapshotService`(6h)、`ClosedPositionIncrementalSyncJob` hot/warm、`ClosedPositionFullResyncJob`(24h)。

快照/特征类：`MarketSnapshotCollectorService`(45s)、`TradeEffectLabelService`(60s)、`WalletFeatureDailyService`(5min)、`BehaviorProfileSnapshotJob`(10min)、`ProfileOrderStatsSnapshotJob`(15min)、`ProfileDiagnosisSnapshotJob`(30min)、`applyActivityDecay`(6h)、`StrategyHealthMonitorJob`(1h)。

审计/报表类（多为 cron）：`SettlementSourceAuditJob`、`ResolutionTriDiffJob`、`LiveReplayDiffJob`、`MarketLiquidityPercentileSnapshotJob`、`WeeklyTopLeaderAutoAllowlistJob`、`ShadowVsLiveWeeklyReportService`、`SlippagePostFactReportJob`、`LeaderDriftAggregationJob`、`LeaderRollingMonitorJob`、`ShadowSettlementBackfillJob`。

共约 **26 个**。

> 注：`MarketSnapshotCollectorService`(45s) 与 `TradeEffectLabelService`(60s) 虽频率较高，但产出只用于离线分析/标注，不在下单关键路径，故归 Tier 3。它们与热路径抢线程，正是必须做池隔离的原因之一。

## 6. 整改方案设计

> 以下为设计方案，按优先级排序；本文档不改动源码。

### 方案 A —【P0】热路径独立线程池隔离

把调度器拆成两个，按 Tier 分流，使 Tier 3 重型任务永远无法占用热路径的线程：

- `hotPathScheduler`：4 线程，专供 Tier 1 的 12 个任务。
- `backgroundScheduler`：维持现有 8 线程（或调大），承载 Tier 2 + Tier 3。

落地方式（任选其一）：

1. Spring 6.1+ 的 `@Scheduled(scheduler = "hotPathScheduler")` 显式指定调度器——改动最小，给 Tier 1 的 12 个方法各加一个属性即可。
2. 用 `SchedulingConfigurer` 分组注册；或将 Tier 1 任务从 `@Scheduled` 改为注册到独立 `ScheduledExecutorService`。

回滚：删除第二个 Bean 即退回单池，无数据副作用。

### 方案 B —【P0】Polymarket API 全局限流器

引入跨任务共享的令牌桶（如 Resilience4j `RateLimiter` 或 Guava `RateLimiter`），在 `PolymarketApiClient` 出口统一限速，按 data / gamma / clob 三端点分别配额。所有任务调用 API 前先取令牌，把"集体退避→集体重试"的抖动改成"平滑排队"。配额值需依据 Polymarket 实际限额设定，建议预留 30% 余量。

### 方案 C —【P1】Cron 错峰

将整点冲突打散，避开 `SettlementSourceAuditJob` 的整点节拍：

| 任务 | 现状 | 建议 |
|---|---|---|
| `WeeklyTopLeaderAutoAllowlistJob` | 每日 06:00 | 每日 06:10 |
| `ShadowVsLiveWeeklyReportService` | 周一 06:00 | 周一 06:40 |
| `LeaderDriftAggregationJob` | 每日 08:00 | 每日 08:20 |
| `LiveReplayDiffJob` | 每日 02:00 | 每日 02:10 |

所有 cron 已是 `${...}` 占位符，**改 `application.yml` 即可，无需改代码**。

### 方案 D —【P1】启动期 / 5 分钟簇错相

给 Tier 2 / Tier 3 的 fixedDelay 任务补 `initialDelay`，把启动瞬间的"惊群"摊开到 0–120s，并让 5min 簇的任务初相错开（如 0s / 20s / 40s / 60s…）。同样优先用配置占位符实现。

### 方案 E —【P2】共享表写入串行化

将 6 个写 `smart_wallet_profile` 的画像/维护任务收敛到一个**单线程顺序执行器**（专用 `ScheduledExecutorService(1)` 或单线程 `backgroundScheduler` 分组），恢复它们之间的串行语义，消除并发写；或对涉及的画像更新加细粒度锁。

### 方案 F —【P2，扩容前必做】分布式锁

横向扩容到多实例前，对所有"有副作用"的任务（下单、领奖、审计、白名单变更等）接入 ShedLock 或 Redis 锁，保证集群内每个任务每周期只跑一次。单实例运行期间可暂不实施，但需在扩容评审清单中列为前置项。

### 落地优先级总览

| 优先级 | 方案 | 解决的风险 | 改动量 |
|---|---|---|---|
| P0 | A 热路径独立线程池 | 风险 1、2 | 中（注解/配置类） |
| P0 | B API 全局限流器 | 风险 4 | 中（API 客户端） |
| P1 | C Cron 错峰 | 风险 3 | 极小（仅改 yml） |
| P1 | D 启动/节拍错相 | 风险 2 | 小（配置为主） |
| P2 | E 共享表写入串行化 | 风险 5 | 中 |
| P2 | F 分布式锁 | 风险 6 | 大（扩容前再做） |
