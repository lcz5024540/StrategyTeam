## 5. 数据质量问题

本报告不使用 `smart_wallet_position` 作为收益主口径，原因是该环境存在以下数据质量问题：

| 检查项 | 异常数 |
|---|---:|
| `position.closed_at < position.opened_at` | 19 |
| `position.cost_basis_usdc = 0` 但 `trade_order.entry_cost_usdc <> 0` | 55 |
| `trade_order.status='OPEN'` 但存在 sell exit_reason | 1 |
| `CLAIMED` 缺失 settled_at | 0 |
| 负 entry cost | 0 |

影响：

- 已结算 position 成本被清零，会导致直接用 position 计算 ROI 时出现失真。
- 19 个 position 的 closed/open 时间倒挂，会污染持仓时长和按日归因。
- 因此前端和报表默认应迁移到 `smart_wallet_trade_order` 生命周期口径，position 仅作为当前持仓状态和实时同步事实表。

## 6. 改进建议

1. 降低 profile 胜率权重，提高内部跟单后胜率和内部跟单 PnL 权重。
   - 例如 `0x2005...75ea` 外部近期胜率很好，但内部跟单胜率只有 36.36%，净亏 -140.6115。
   - 例如 `0x9f2...ca8` profile 近 30 日 100% 胜率，但单笔跟单直接 -100%。

2. 对 `CLAIMED` 结算归零建立地址级和市场级降权。
   - 17 笔结算归零亏损 -383.1100，是本轮最大失误来源。
   - 地址若出现连续结算归零，应进入冷却或只允许提前退出型 paper。

3. 将 observe-only 地址从 paper canary 进一步降仓。
   - 本轮最大亏损地址和最大盈利地址都被行为画像标为 `NOISE_OR_INSUFFICIENT / OBSERVE_ONLY`。
   - 这类地址可以用于研究，但不应作为真实资金主信号。

4. 强化低价赔率段过滤。
   - `<0.08` 和 `0.08-0.18` 两个价格桶合计 PnL -93.2442，胜率分别只有 25% 和 20%。
   - 低价单除非有明确事件型信息优势，否则应默认 paper 或拒绝。

5. 提前过滤市场生命周期。
   - 7,417 条 SKIPPED 来自市场已结算、已关闭或不接单。
   - 候选生成阶段就应查 `smart_wallet_market_info.market_lifecycle / closed / accepting_orders`，减少后端 follow task 噪音。

6. 修复 position 与 trade_order 的展示口径。
   - 修复 `closed_at < opened_at`。
   - 修复已结算 position 成本清零导致的 ROI 失真。
   - 前端订单列表和分析报表默认读取 `smart_wallet_trade_order`，不要从 `smart_wallet_position.cost_basis_usdc` 反推历史收益。

## 8. 复核口径

- 订单胜率：`smart_wallet_trade_order.status <> 'OPEN' AND total_pnl_usdc > 0`。
- 订单失误率：`smart_wallet_trade_order.status <> 'OPEN' AND total_pnl_usdc < 0`。
- OPEN 仓位只列风险暴露，不计入已关闭胜率/失误率。
- 候选拦截只用于数据库层面信号质量复盘，不计入订单胜率。
- `smart_wallet_position` 只用于数据质量检查，不作为历史收益主口径。
