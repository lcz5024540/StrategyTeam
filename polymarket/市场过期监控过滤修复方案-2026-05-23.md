# Polymarket 监控视图「市场过期」过滤 — 修复方案

> 用途：供复核「修复是否合理」。文末第五节是**需要你拍板的判断点**，建议先看结论再看细节。

---

## 一、现象

`SmartWalletMarketMonitoringServiceTest` 三个用例失败：

| 用例 | 期望 | 实得 |
|------|------|------|
| `shouldExcludeExpiredMarketsFromRefreshCandidates` | `[market-live]` | `[market-live, market-expired]` |
| `shouldKeepExcludingClosedResolvedAndEndedMarkets` | `[]` | `[market-ended-task]` |
| `shouldHideExpiredMarketsEvenIfPersistedSnapshotStillSaysActive` | `0` 条 | `1` 条 |

共同点：三个用例都构造了「`marketEndAt` 已是过去时间、但 `lifecycle` 仍为 `ACTIVE`」的市场，并断言它应被监控视图隐藏 / 从候选中排除；而当前生产代码没有隐藏它。

---

## 二、调查：生产代码实际怎么判「活跃」

`SmartWalletMarketMonitoringService` 中所有「是否纳入监控 / 候选」的判定，都只看生命周期，不看 `marketEndAt`：

```java
// 显示用
private boolean shouldDisplayActiveMarket(MarketStateSnapshot snapshot, Long marketEndAt) {
    return snapshot != null && snapshot.isActive();      // ← marketEndAt 参数收了、但不用
}

// 候选用
private boolean shouldTrackCandidateMarket(MarketAccumulator accumulator, MarketStateSnapshot snapshot) {
    if (snapshot != null) return snapshot.isActive();
    return isActiveLifecycle(accumulator.marketLifecycle);
}

// 已知市场用
private boolean shouldTrackKnownMarket(SmartWalletMarketInfoEntity marketInfo) {
    // 仅检查 resolvedOutcome / closed / acceptingOrders / lifecycle —— 无 endAt 判断
}
```

而 `MarketStateSnapshot.isActive()`：

```java
public boolean isActive() {
    return LIFECYCLE_ACTIVE.equalsIgnoreCase(marketLifecycle);
}
```

所以：一个 `lifecycle=ACTIVE` 的市场，即使 `marketEndAt` 已过期，监控视图仍把它当活跃市场显示 / 纳入候选。

---

## 三、关键证据：这是有意的设计演进，不是回归

三条证据指向「有意修改」而非「不小心改坏」：

**证据 1 — `shouldDisplayActiveMarket` 的 `marketEndAt` 参数收了不用。**
如果是「不慎漏掉 endAt 判断」，重构时通常会把不再需要的参数一并删除。保留参数、只是方法体里不引用它，是「刻意去掉判断逻辑、签名留作调用方兼容」的典型特征。

**证据 2 — 同一设计哲学在交易侧已有带签名的明文记录。**
`SmartWalletSignalRiskService` 的 G6 闸门里有这样一段注释：

> ```
> // 2026-05-18 ray@cowork: 修复 G6_MARKET_EXPIRED 误判 (占 56% 拒绝率)。
> // Polymarket 长尾市场 endAt 经常陈旧, 但 lifecycle=ACTIVE+accepting_orders=true 仍可正常交易。
> // 只有 marketState 同时确认非活跃或不接单时, 才视为真过期。
> ```

即：Polymarket 长尾市场的 `endAt` 字段不可靠，曾导致 56% 的下单被误拒，已被有意降级为「非权威信号」。

**证据 3 — 一致性。**
监控服务里四个过滤方法（`shouldDisplayActiveMarket` / `shouldTrackCandidateMarket` / `shouldTrackByKnownFacts` / `shouldTrackKnownMarket`）无一检查 `endAt`，全部以 `lifecycle` / `closed` / `resolvedOutcome` / `acceptingOrders` 为准。系统性一致，而非个别遗漏。

**结论：** 按分类框架，这属于「**前者：原逻辑有意修改**」。监控视图的「过期」判定标准，已从 `marketEndAt < now` 切换为 `lifecycle 非 ACTIVE`。三个用例写于该切换之前，断言的是旧契约，因此失败。**未发现生产回归。**

---

## 四、修复方案（两个备选，已采用 A）

### 方案 A（已采用）——把测试改为按新契约表达「非活跃」

三个用例的**核心意图**——「不可交易的市场应从监控视图隐藏 / 排除」——在新契约下依然成立、依然值得测试。只需把「过期」的**表达方式**，从旧的「过去式 `endAt`」换成新的「非活跃 `lifecycle`」即可。这样测试继续守护其真正的目标逻辑，只是用当前正确的信号来表达。

### 方案 B（未采用，留给你判断）——改生产代码、保留原测试

如果你认为**监控视图就应该按 `endAt` 隐藏过期市场**，那么修复点不在测试、而在生产代码：需要在 `shouldDisplayActiveMarket` / `shouldTrackCandidateMarket` 等处重新加回 `marketEndAt != null && marketEndAt < now` 的判断；三个原始用例则应原样保留（它们恰好就是这条契约的回归测试）。

---

## 五、需要你确认的判断点 ⚠️

这是复核的核心。G6 那条修复的语境是**交易闸门**（不要因 `endAt` 陈旧而误拒下单）。把同一条「信任 `lifecycle`、忽略 `endAt`」的原则推广到**监控仪表盘的可见性**，是相关、但并不完全等价的决定：

- **支持现状（忽略 endAt）：** `endAt` 不可靠；若市场实际仍 `lifecycle=ACTIVE & acceptingOrders=true`，它就是可交易的，监控盘理应继续显示——否则会出现「能下单的市场却不在监控列表」的盲区。
- **反对现状（应按 endAt 隐藏）：** 监控盘是给人看的；一个名义结束时间早已过去的市场长期挂在「活跃」列表里，可能造成误读——尤其当 `lifecycle` 因元数据同步延迟、尚未从 `ACTIVE` 翻成 `CLOSED` 时，监控盘会短暂显示一个「事实上已结束、形式上仍 ACTIVE」的市场。

**我的修复采用了方案 A（与生产现状对齐，认定现状是有意设计）。**
如果你复核后倾向方案 B，请告诉我——我会改生产代码（重新加回 endAt 判断）并把这三个测试回退为原样。

## 六、修复明细（方案 A，已落地）

三处改动，均在 `SmartWalletMarketMonitoringServiceTest`，未触碰生产代码：

| 用例 | 旧构造（隐含旧契约） | 新构造（对齐新契约） |
|------|---------------------|---------------------|
| `shouldHideExpiredMarketsEvenIfPersistedSnapshotStillSaysActive` <br>→ 重命名为 `shouldHideMarketsWhosePersistedSnapshotIsNoLongerActive` | snapshot：`lifecycle=ACTIVE` / `acceptingOrders=true` / `endAt=now-60s` | snapshot：`lifecycle=CLOSED_UNRESOLVED` / `acceptingOrders=false` / `closed=true` |
| `shouldExcludeExpiredMarketsFromRefreshCandidates` | `market-expired` snapshot：`lifecycle=ACTIVE` / `acceptingOrders=true` / `endAt=now-60s` | `market-expired` snapshot：`lifecycle=CLOSED_UNRESOLVED` / `acceptingOrders=false` / `closed=true` |
| `shouldKeepExcludingClosedResolvedAndEndedMarkets` | `market-ended-task` snapshot：`activeSnapshot(...)`（即 `ACTIVE`），仅靠 marketInfo 的过去式 `endAt` 表达「ended」 | `market-ended-task` snapshot：内联 `lifecycle=CLOSED_UNRESOLVED` / `acceptingOrders=false` / `closed=true` |

关于第一个用例的**重命名**：旧名 `...EvenIfPersistedSnapshotStillSaysActive`（「即使快照仍说 ACTIVE 也隐藏」）在新契约下变成事实性错误——新契约下，快照说 `ACTIVE` 就是活跃。为保持测试名诚实，改名为 `shouldHideMarketsWhosePersistedSnapshotIsNoLongerActive`（「快照已非活跃则隐藏」）。

第三个用例命名里的「Ended」予以保留：真实链路中，一个已结束的市场最终会被元数据同步标记为 `CLOSED`——用 `CLOSED_UNRESOLVED` 表达「ended」与现实一致。

每处改动都加了中文注释，说明「契约已从 endAt 切换为 lifecycle」，便于后续维护者理解。

---

## 七、验证

修复后 `SmartWalletMarketMonitoringServiceTest` **12/12 全绿**（使用沙箱内 JDK 17 + Maven + JUnit Platform 实跑）。三个用例的核心意图——「关闭 / 已结算 / 不接单的市场被排除」——仍由 lifecycle 维度的断言守护。

---

## 八、一句话总结

监控视图「过期」判定的契约已（在测试编写之后）从「`endAt < now`」有意切换为「`lifecycle` 非 `ACTIVE`」，与交易侧 G6 的「`endAt` 不可靠」修复同源。修复采用「让测试对齐新契约」（方案 A）。**唯一需要你确认的是：监控仪表盘的可见性是否也应遵循这条原则——若否，则应改生产代码（方案 B）。**
