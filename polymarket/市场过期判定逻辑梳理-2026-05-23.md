# Polymarket 跟单策略 — 市场过期判定逻辑梳理

**梳理时间**：2026-05-23
**代码范围**：`coin-strategy-job` / `coin-strategy-common`（job 服务）
**关联背景**：运行分析报告显示 5.13 以来 SKIPPED 跟单任务中 **94%（8,515 条）** 的拒绝原因是 `MARKET_RESOLVED`，本文梳理这一判定是如何产生的，并诊断问题。

---

## 一、一句话结论

系统判定一个市场"已过期/不可交易"，**完全依据 Polymarket API 返回的三个标志位**——`resolvedOutcome`（结算结果）、`closed`（已关闭）、`acceptingOrders`（是否接单）——折算成 `marketLifecycle` 生命周期字段。**市场结束时间 `marketEndAt` 几乎不参与"是否过期"的判定**。判定逻辑本身是准确的，真正的问题是**判定发生得太晚**：等跟单任务走到市场检查这一步时，快市场（电竞、网球）往往已经结算。

---

## 二、判定的数据模型

核心模型是 `MarketStateSnapshot`（`common-service/.../smartwallet/model/MarketStateSnapshot.java`），它是从 `smart_wallet_market_info` 表 + Polymarket Gamma API 组装出来的市场状态快照。

关键字段与方法：

| 字段 / 方法 | 含义 |
|---|---|
| `marketLifecycle` | 生命周期，三种取值：`ACTIVE` / `CLOSED_UNRESOLVED` / `RESOLVED` |
| `closed` | API 标志：市场是否已关闭 |
| `acceptingOrders` | API 标志：市场是否还接受下单 |
| `resolvedOutcome` | 结算结果（非空即代表已结算） |
| `marketEndAt` | 市场名义结束时间（毫秒时间戳） |
| `isActive()` | `lifecycle == ACTIVE` 才算"活跃可跟" |
| `blockingReasonCode()` | `RESOLVED → MARKET_RESOLVED`；`!acceptingOrders → MARKET_NOT_ACCEPTING_ORDERS`；其余 → `MARKET_CLOSED` |
| `unknown()` | 兜底快照：marketId 缺失时返回 `ACTIVE + acceptingOrders=true`（**即"未知 = 当作可交易"**） |

### 生命周期是如何算出来的

`SmartWalletMarketStateService.resolveLifecycle()`（`SmartWalletMarketStateService.java:461`）——用于 API 新数据：

```
if (resolvedOutcome 非空)     → RESOLVED
else if (closed == true)      → CLOSED_UNRESOLVED
else if (acceptingOrders==false) → CLOSED_UNRESOLVED
else                          → ACTIVE
```

> **注意**：该方法签名里带了 `Long marketEndAt` 参数，但方法体内**完全没有使用它**。也就是说，市场结束时间过了多久，都不会让生命周期变成"过期"。

`resolvePersistedLifecycle()`（`:282`）——用于读取数据库已持久化的行，规则基本一致，额外多一条：若数据库里 `marketLifecycle` 已经是 `RESOLVED`，则保持 `RESOLVED`（结算状态不回退）。

## 三、判定发生在哪里：两道关卡 + 一个数据修复 Job

市场过期判定在跟单链路里出现在**两个位置**，加上一个后台数据刷新 Job。

### 关卡一：S4 市场检查（跟单任务生成阶段）

位置：`SmartWalletFollowTaskService.java:918-932`。这是**绝大多数 `MARKET_RESOLVED` 跳过的来源**。

```
SmartWalletMarketInfoEntity marketInfo = ensureMarketInfoForEvent(event);
MarketStateSnapshot marketState = refreshMarketState(event);   // 取市场状态
if (!marketState.isActive()) {                                 // 非 ACTIVE 即拦截
    createLifecycleSkippedTask(event, candidate, marketInfo, marketState);
    ... 日志 firstRejectGate=G6_MARKET_NOT_ACTIVE, blockerCategories=MARKET_STATE
    return;
}
```

`createLifecycleSkippedTask()`（`:1389`）写入一条跟单任务：

- `status = SKIPPED`
- `primarySkipReason = "NON_TRADABLE"`、`skipReasonTags = "NON_TRADABLE"`（**无论是 RESOLVED、NOT_ACCEPTING 还是 CLOSED，这里一律写死 NON_TRADABLE**）
- `errorMessage = marketState.blockingReasonMessage()`——这里才区分出 `[MARKET_RESOLVED] Market is already resolved.` 等具体文案
- `recommendedStakeUsdc = 0`

> 这解释了运行报告中"9,031 条 SKIPPED 的 `primary_skip_reason` 全是 `NON_TRADABLE`"——细分原因只在 `error_message` 文本里，DB 字段层面被抹平了。

#### S4 之前还有一道 S2.5 入口新鲜度闸门

`SmartWalletFollowTaskService.java:884-903`：在 S3/S4 之前，先按交易事件的 `openedAt` 做硬判定——

```
if (signalAgeMs > maxIngestSignalAgeMs)   // 默认 10800 秒 = 3 小时
    → 落 SKIPPED，firstRejectGate=G5_SIGNAL_STALE_INGEST
```

代码注释明确写道：这道闸门是**专门为了避免历史成交（停机积压重放、warm 回填等）被 S4 误归因成 `MARKET_RESOLVED`** 而加的。但阈值是 **3 小时**——只要事件不超过 3 小时旧，仍会放行到 S4。

### 关卡二：Gate 6 市场状态/时间窗口（风控评估阶段）

位置：`SmartWalletSignalRiskService.java:410-478`。这是更深一层的风控网关，**同时检查生命周期和时间**：

```
MarketStateSnapshot marketState = refreshMarket(...);
if (!marketState.isActive())  → 拒绝 G6_MARKET_NOT_ACTIVE

Long endAt = marketState.marketEndAt();
if (endAt > 0) {
    remainingMs = endAt - now;
    if (remainingMs <= 0) {                    // 已过名义结束时间
        // 2026-05-18 ray@cowork 修复：只有 lifecycle 也非活跃/不接单时才算真过期
        if (!isActive() || !acceptingOrders)   → 拒绝 G6_MARKET_EXPIRED
        else                                   → 放行（[MARKET_END_AT_STALE_BUT_ACTIVE]）
    } else if (remainingMs > 365 天)           → 拒绝 G6_MARKET_END_DATA_QUALITY
    else if (remainingMs > 72 小时)            → 拒绝 G6_MARKET_END_TOO_FAR
} else {                                       // endAt 为空
    强制 forceRefresh 再查一次，复用同样规则
    （G6_MARKET_NOT_ACTIVE_AFTER_FORCE_REFRESH / G6_MARKET_EXPIRED_AFTER_FORCE_REFRESH）
}
```

**关键点**：`:425` 处有一条 2026-05-18 的修复注释——"修复 G6_MARKET_EXPIRED 误判（占 56% 拒绝率）。Polymarket 长尾市场 endAt 经常陈旧，但 lifecycle=ACTIVE 仍可正常交易"。修复后，**"名义结束时间已过"本身不再构成拒绝**，必须叠加 `lifecycle 非活跃`或`不接单`才拒。等于把"基于时间的过期判定"基本短路掉了。

### 数据修复 Job：MarketInfoEndAtRefreshJob

位置：`MarketInfoEndAtRefreshJob.java`。每 **10 分钟**扫描 200 条 `lifecycle=ACTIVE 但 endAt 缺失/陈旧`的市场，强制从 Gamma API 重新拉取 `endAt` 写回。

其类注释揭示了一段历史：market_info 表迁移后没有补建周期刷新机制，导致 **76% 的行 `endAt=NULL`，G6_MARKET_EXPIRED 一度占到拒绝率的 56%**。该 Job + 上面的 5-18 短路修复，是同一个问题的两手应对。

## 四、完整调用链路

```
交易事件 trade_event
   │
   ▼  S1 摄取
   │
   ▼  S2.5 入口新鲜度闸门  ── openedAt 超 3 小时 → SKIPPED(G5_SIGNAL_STALE_INGEST)
   │
   ▼  S3 候选智能增强
   │
   ▼  S4 市场检查  ──────────  refreshMarketState() → !isActive()
   │                            → createLifecycleSkippedTask()
   │                            → SKIPPED / NON_TRADABLE / [MARKET_RESOLVED]   ★ 94% 在此
   │
   ▼  S5 风控评估
        └─ Gate 6 市场状态/时间窗口
              ├─ !isActive()            → G6_MARKET_NOT_ACTIVE
              ├─ endAt 已过 & 非活跃     → G6_MARKET_EXPIRED
              ├─ endAt 距今 > 365 天     → G6_MARKET_END_DATA_QUALITY
              └─ endAt 距今 > 72 小时    → G6_MARKET_END_TOO_FAR

市场状态来源：refreshMarket()
   ├─ 先查 smart_wallet_market_info 表
   ├─ 若最近同步 < 60 秒（DEFAULT_METADATA_STALE_MS）且字段完整 → 用缓存
   └─ 否则调 Polymarket Gamma API → 重建快照 → 写回表
```

## 五、关键参数一览

| 参数 | 默认值 | 作用 | 位置 |
|---|---|---|---|
| `maxIngestSignalAgeSeconds` | **10800 秒（3 小时）** | S2.5 入口新鲜度上限，超过即判历史成交 | `SmartWalletProperties:462` |
| `DEFAULT_METADATA_STALE_MS` | **60000 毫秒（60 秒）** | 市场状态缓存有效期，过期即重新调 API | `SmartWalletMarketStateService:41` |
| `maxHoursToMarketEnd` | 72 小时 | 距结算太远则拒（G6_MARKET_END_TOO_FAR） | `SmartWalletProperties:708` |
| `obviouslyFutureMarketEndDays` | 365 天 | endAt 异常遥远则判数据质量问题 | `SmartWalletProperties:953` |
| market-info-refresh `interval-ms` | 600000（10 分钟） | endAt 修复 Job 频率，单批 200 条 | `MarketInfoEndAtRefreshJob:45` |

## 六、问题诊断

结合运行报告"MARKET_RESOLVED 占 94%"的发现，逐条诊断。

### 6.1 判定准确，但触发太晚（核心矛盾）

`MARKET_RESOLVED` 并不是"误判"——市场确实已经结算了。问题在于**判定点（S4）位于一条很长的链路末端**：S1 摄取 → S2.5 → S3 候选增强 → S4。叠加约 13–40 分钟的端到端摄取延迟（见运行报告），等流程走到 S4，电竞单图、网球单盘这类**分钟级结算的快市场早已结算**。换句话说：不是判错了，是来不及。

### 6.2 三小时摄取窗口对快市场过于宽松

S2.5 闸门用 **统一的 3 小时**阈值。3 小时对政治、宏观这类长周期市场合理，但对快市场是灾难——一个电竞市场的整个寿命可能不到 1 小时。结果是：大量"在到达 S4 之前注定会结算"的事件，因为还没满 3 小时，照样被放行进 S4，最终全部变成 `MARKET_RESOLVED`。**这是 94% 占比的直接放大器。**

### 6.3 时间维度的过期判定已被实质短路

`resolveLifecycle()` 不使用 `marketEndAt`；G6 的 5-18 修复又把"endAt 已过"从拒绝条件里摘除。两处叠加，**系统对市场过期的判断 100% 依赖 API 的 `resolvedOutcome`/`closed`/`acceptingOrders`**。这避免了误杀 endAt 陈旧的长尾市场（这是修复的本意），但副作用是：对一个"已经实质结束、但 Polymarket 尚未把标志位刷新过来"的市场，系统**无法借助时间提前规避**，只能等 API 状态翻转——而那时跟单早已没有意义。

### 6.4 拒绝原因在 DB 层被抹平

S4 拦截一律写 `primary_skip_reason = NON_TRADABLE`，导致数据库层面无法区分 RESOLVED / NOT_ACCEPTING / CLOSED，可观测性下降（运行报告里只能靠 `error_message` 文本反查才知道 94% 是 RESOLVED）。

### 6.5 强依赖数据新鲜度与 API 可用性

判定链路依赖：`market_info` 表数据质量 + 60 秒缓存 + Gamma API 可用性。一旦 API 失败，快照会回退到旧持久化数据，或在 marketId 缺失时回退到 `unknown() = ACTIVE`——**"未知"被当作"可交易"**，存在把已结算市场误判为活跃的风险（虽方向相反，但同样是判定不可靠的表现）。`MarketInfoEndAtRefreshJob` 注释里"76% 行 endAt=NULL"正是数据新鲜度欠债的实证。

### 6.6 单事件重复刷新市场状态

`ensureMarketInfoForEvent`、S4 的 `refreshMarketState`、G6 的 `refreshMarket`、以及 endAt 为空时的 forceRefresh——同一事件最多触发 4 次市场状态解析。60 秒缓存能挡住大部分，但仍是延迟与 API 配额的浪费。

### 6.7 停机会被判定逻辑成倍放大

服务停机（如 5.20–5.22 的 40 小时中断）期间事件积压，恢复后批量重放：超 3 小时的→S2.5 拦成 STALE；**未超 3 小时、但对应快市场已结算的→全部涌入 S4 变成 `MARKET_RESOLVED`**。运行报告中 5/22 当天 7,419 条 SKIPPED 即此现象。

## 七、改进建议

按"性价比 / 见效速度"排序：

1. **【最高性价比】按市场类型分级摄取新鲜度窗口**：把 S2.5 的统一 3 小时改为按 `normalizedCategory` 分级——SPORTS / 快事件用很短窗口（如 5–10 分钟），POLITICS / MACRO 等长周期市场才保留数小时。可一次性砍掉大量"注定 MARKET_RESOLVED"的无效流转。

2. **市场状态检查前移**：把 lifecycle 检查从 S4 提到 S3 候选增强**之前**，对已结算市场尽早 return，避免把候选增强、智能富集等重活浪费在死市场上（也顺带降低 6.6 的重复刷新）。

3. **引入基于 `marketEndAt` 的快市场预筛**：对 `endAt` 已过、且市场类型为快市场的事件直接早退，不必等 API 的 `resolvedOutcome` 翻转。注意与 5-18 修复的边界——仅对快市场类型启用，长尾市场仍走原逻辑，避免重新引入误杀。

4. **降低端到端延迟（治本）**：开启 Polymarket WebSocket 实时推送（当前 `enable-ws-client=false`）或缩短轮询周期。摄取延迟从 15–40 分钟压到分钟级，才是真正减少 `MARKET_RESOLVED` 的根本手段。

5. **S4 拒绝原因细分**：`createLifecycleSkippedTask` 按 `blockingReasonCode()` 写入 `primary_skip_reason`（MARKET_RESOLVED / MARKET_NOT_ACCEPTING_ORDERS / MARKET_CLOSED），恢复 DB 层可观测性。

6. **提升 market_info 刷新覆盖**：确保 `MarketInfoEndAtRefreshJob` 稳定运行、必要时提高频率/批量，把 `endAt`、`closed`、`acceptingOrders` 的新鲜度欠债补上——它是上面所有判定的数据地基。
