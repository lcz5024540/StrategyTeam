# 三个追问的代码修复方案

---

## Q1：合并等待太久导致市场结束 — 解决方案

### 现在的时间链路（实测延迟拆解）

```text
Leader 在 Polymarket 下单 (T0)
  ↓ 延迟 5~14 分钟（trade_event sync 周期 ~30min + dynamic interval）
trade_event 入库 (T1 = T0 + 5~14min)
  ↓ IntentAggregation 启动 windowMinutes=5 分钟等碎片
合并完成 (T2 = T1 + 0~5min)  
  ↓ resolveFollowDelayMs，fragment_count>1 时延迟 executionDelaySeconds=30s
scheduledAt 触发风控评估 (T3 = T2 + 30s)
```

**总延迟 = 5~20 分钟**。Polymarket 上很多市场（FAST_EVENT）endAt 距下单时只剩 10-30 分钟 → 我方决策时早已过期。

### 配置位置 + 默认值

`SmartWalletProperties.IntentAggregationConfig`：
```java
private int windowMinutes = 5;             // 合并窗口 5 分钟
private int executionDelaySeconds = 30;    // 多碎片场景再延迟 30 秒
private BigDecimal maxStakeMultiplier = 3; // 最多放大 3 倍
```

### 解决方案（按工作量从低到高）

**方案 A · 改运行时配置（最快，5 分钟）**

把 `smart-wallet.intent-aggregation` 写到 `/opt/coinstrategy/smart-wallet/config/application-test.yml`：

```yaml
smart-wallet:
  intent-aggregation:
    enabled: true
    window-minutes: 2           # 5min → 2min
    execution-delay-seconds: 10 # 30s → 10s（仅多碎片时）
    min-aggregated-trigger-usdc: 5
    max-stake-multiplier: 3
```

**预期效果**：合并窗口 5→2 分钟，省 3 分钟；执行延迟 30→10 秒省 20 秒；**总延迟从 5~20 min 降到 3~17 min**。

**方案 B · 代码改动：FAST_EVENT 跳过 executionDelay（30 分钟）**

`SmartWalletFollowTaskService.resolveFollowDelayMs` (line 1982) 改一下，当 marketType=FAST_EVENT 时直接返回 0：

```java
private long resolveFollowDelayMs(int fragmentCount) {
    // 2026-05-18 ray@cowork: FAST_EVENT 市场剩余时间通常 < 30 min, 不能再 wait 30s
    if (currentMarketType == FAST_EVENT) return 0;
    ...
}
```

但这需要在 createFollowTaskIfQualified 里把 marketType 传下来，多一点改动。

**方案 C · 缩短 sync 周期到 5 分钟（结合 Q3 的改动）**

让 trade_event 入库延迟从 5~14 min → 2~5 min。

### 推荐组合：A + C，先做 A

## Q2：不活跃白名单为什么没有跟单

### 实测数据（部署后 64 分钟）

| 钱包 | last_trade | 部署后 trade_event 入库 |
|------|------------|------------------------|
| `0x2005d16a` | 27 分钟前 | **54 条** |
| `0x9d84ce0306` | 1.5 小时前 | 1 条 |
| `0xfbfd14dd4b` | 3 小时前 | 0 条 |
| `0x51fd8f0358` | 11 小时前 | 0 条 |
| `0x9f2fe025f8` | 35 小时前 | 0 条 |

### 根因（不是 1 个原因，是 3 个叠加）

**1. trade_event 同步是"增量"的，需要 leader 有"新的"交易**

`PolymarketWalletDiscoveryService.refreshHotWallet` 读取 `wallet.getLastEventSyncAt()` 作为水位线，只拉这个时间之后的新 trade。如果 leader 没有新交易，sync 进来 0 条。

部署后 64 分钟内：
- `0x9f2fe025f8`：上次活动 35 小时前 → 中间没新交易 → 部署后 0 条 ✓ 符合
- `0xfbfd14dd4b`：上次活动 3 小时前，但部署前的 sync 在 21:22-21:56 之间应该已经把这条拉过来了 → 部署后没新交易 → 部署后 0 条 ✓ 符合

**2. 即使他们有事件入库，也会被同样的 G6 / G3 / G10 拒**

我看了部署前几天的历史 task：4 个不活跃钱包的事件**之前都生成过 task**，但**全部 PAPER_SHADOW**，被同样的 `G6_MARKET_EXPIRED` / `G3_PRICE_OUT_OF_RANGE` / `G10_KELLY_NEGATIVE_EV` 拒。

也就是说**即使 5 个老白名单全部活跃**，按当前 G6 逻辑也跟不了单。

**3. archetype 都是 NOISE_OR_INSUFFICIENT**

这 5 个老白名单（包括 `0x2005d16a`）的钱包画像都很差 — settlementCompletionRate ≈ 0.0054，意味着他们的仓位**几乎不结算**。系统判定为低质量信号源。

### 解决方案

跟 Q1/Q3 共享：**修复 G6 + 缩短延迟**之后，这 4 个不活跃白名单的"零星交易"才有机会跟到。

如果想立即看到结果，可以再加 1 步：
- 用 SQL 查这 4 个钱包**历史所有 trade_event** 的 marketId
- 看哪些市场 endAt 还在未来（依然可交易）
- 那些 task 应该可以 retry（但代码里没有 task retry 机制，需要新加）

**实际可操作的最简单的方案**：
1. 修 G6 让"endAt 过期但 lifecycle=ACTIVE+accepting_orders=true"通过 → 等这 4 个钱包下一次任何交易就能直接产单
2. 不要寄希望于"补救"过去的事件

## Q3：G6_MARKET_EXPIRED 在哪一步拦截 + 逻辑是否有问题

### 代码精确位置

`SmartWalletSignalRiskService.java`，Gate 6 在 line 410-464：

```java
// ── Gate 6: 市场状态 / 时间窗口 ──
MarketStateSnapshot marketState = marketStateService.refreshMarket(...);

if (!marketState.isActive()) {
    accepted = false;
    firstRejectGate = "G6_MARKET_NOT_ACTIVE";
    reasons.add(marketState.blockingReasonMessage());
}

Long endAt = marketState.marketEndAt();
if (endAt != null && endAt > 0) {
    long remainingMs = endAt - System.currentTimeMillis();
    if (remainingMs <= 0) {
        accepted = false;
        firstRejectGate = "G6_MARKET_EXPIRED";       // ← 罪魁祸首
        reasons.add("Market is already at or past expected end time.");
    } else { 
        // ... maxHours / obviousFuture 检查
    }
} else if (accepted) {
    // marketEndAt 为空时强制 forceRefresh → G6_..._AFTER_FORCE_REFRESH
}
```

### 逻辑确实有问题

**问题 1**：`endAt <= now` 直接判定为过期，**不看 marketState 的其它字段**。

`MarketStateSnapshot` 有 3 个独立的字段：
```java
public record MarketStateSnapshot(
    Long marketEndAt,           // 时间戳
    String marketLifecycle,     // ACTIVE / CLOSED_UNRESOLVED / RESOLVED
    boolean acceptingOrders,    // 是否还在接单
    boolean closed,             // closed 标志
    ...
)

public boolean isActive() {
    return LIFECYCLE_ACTIVE.equalsIgnoreCase(marketLifecycle);
}
```

**`isActive()` 只看 lifecycle 标志**，`endAt` 是另一个独立维度。

但 Polymarket 上很多市场存在**数据不一致**：
- `lifecycle=ACTIVE` + `acceptingOrders=true` + `closed=false` ← 真的可交易
- 但 `marketEndAt` 是几天前的旧值（Polymarket 自己没更新这个字段）

**当前代码会把这种数据问题误判成"市场过期"，拒绝可以正常下单的市场**。

**问题 2**：`isActive()` 和 `endAt` 检查是分离的，前者没有 short-circuit 后者。

### 修复方案（5 行代码）

在 line 424 的 `if (remainingMs <= 0)` 加一个 short-circuit，**只在市场也真的不活跃时**才判定过期：

```java
if (endAt != null && endAt > 0) {
    long remainingMs = endAt - System.currentTimeMillis();
    if (remainingMs <= 0) {
        // 2026-05-18 ray@cowork: 修复 endAt 过期但市场仍开放的误判。
        // Polymarket 上不少长尾市场 endAt 是陈旧值, 但 lifecycle=ACTIVE+accepting_orders=true 仍可交易。
        // 只有当 marketState 也确认非活跃时, endAt 过期才是真的过期。
        if (!marketState.isActive() || !marketState.acceptingOrders()) {
            accepted = false;
            if (firstRejectGate == null) firstRejectGate = "G6_MARKET_EXPIRED";
            reasons.add("Market is already at or past expected end time.");
        } else {
            // endAt 过期但市场仍活跃, 视为数据不一致, 放行
            reasons.add("[MARKET_END_AT_STALE_BUT_ACTIVE] endAt=" + endAt 
                + " in past but lifecycle=ACTIVE & acceptingOrders=true; accepting follow.");
        }
    } else {
        // ... maxHours / obviousFuture 检查
    }
}
```

同样的逻辑要应用到 line 455 的 `G6_MARKET_EXPIRED_AFTER_FORCE_REFRESH`：

```java
if (freshEndAt != null && freshEndAt > 0 && freshEndAt <= System.currentTimeMillis()) {
    // 2026-05-18 ray@cowork: 同上, force refresh 后 endAt 过期也要看 lifecycle
    if (!freshState.isActive() || !freshState.acceptingOrders()) {
        accepted = false;
        if (firstRejectGate == null) firstRejectGate = "G6_MARKET_EXPIRED_AFTER_FORCE_REFRESH";
        reasons.add("[MARKET_END_AT_MISSING_FORCE_REFRESH] marketEndAt was null; forced refresh reveals market is already expired.");
        endAt = freshEndAt;
    } else {
        reasons.add("[MARKET_END_AT_STALE_BUT_ACTIVE_AFTER_FORCE_REFRESH] endAt past but market still active.");
        endAt = freshEndAt;
    }
}
```

### 预期效果

按今天的拒绝码分布，G6_MARKET_EXPIRED + G6_MARKET_EXPIRED_AFTER_FORCE_REFRESH 占 **56%**。修复后这部分中：
- "真的过期"的市场（lifecycle=RESOLVED 等）继续被拒
- "数据陈旧但实际可交易"的市场（lifecycle=ACTIVE）会被放行

预计 **G6 拒绝率从 56% → 20-30%**。剩下的 G6 拒因变成 G6_MARKET_NOT_ACTIVE / G6_MARKET_END_TOO_FAR 等"真过期"。
