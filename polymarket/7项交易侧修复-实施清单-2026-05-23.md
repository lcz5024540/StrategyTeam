## ⚠️ 重要风险登记 —— 修复四延后的资金敞口（务必勿遗忘）

> **决策（2026-05-23）**：先启动 **方案 A**（信任 lifecycle、忽略 endAt，已是生产运行状态），**修复四延后**。延后期间存在真实资金敞口，特此严正登记。

**敞口是什么**：方案 A 完全不看 `marketEndAt`。从「快市场实际结束」到「Polymarket Gamma 把 `closed` 翻成 true」之间有一个**滞后窗口**（UMA 预言机提案 + 争议窗口，数十分钟到数小时）。窗口内 `lifecycle` 仍报 ACTIVE → 方案 A 会**放行**跟单。

**后果**：对快市场（SPORTS / 电竞，寿命常仅几十分钟）——会对一个**事实上已结束、胜负基本已定**的市场下跟单单。订单要么挂单不成交，要么在已定盘的盘口成交 = **直接亏损**。市场寿命越短，滞后窗口占其总寿命比例越大，敞口越显著。

**定性**：这**不是数据质量问题，是会赔钱的执行风险**。在修复四落地前，此敞口持续存在。

**解除路径**：已在 `SmartWalletFollowTaskService.createFollowTaskIfQualified` 埋下 `[FOLLOW_MARKET_AUDIT]` 结构化审计日志（记录每笔跟单信号的「开单时间 / 信号年龄 / 市场是否关闭 / lifecycle / endAt」）。运营 grep 该日志做统计后：
- 若数据证实「信号新鲜（signalAgeSec 小）但 marketClosedAtProcessing=true」在快市场上**确有发生** → lifecycle 滞后被证实 → **必须实施修复四**；
- 若快市场基本不出现该情况 → lifecycle 判定足够及时 → 方案 A 可长期保留。

**在拿到上述统计结论之前，本敞口不得被遗忘。** 详见下方「修复四」章节与第四节「待确认 #1」。

## 修复一（P0）：摄取新鲜度窗口按市场类别分级

**对应问题 6.2** — S2.5 入口闸门用统一 3 小时（`maxIngestSignalAgeSeconds=10800`），对寿命不足 1 小时的快市场过于宽松。

**当前状态**：⚠️ 部分。S2.5 闸门已存在（`SmartWalletFollowTaskService` S2.5 段、`maxIngestSignalAgeMs():1105`），但为统一阈值，未分级。

### 方案

把单一阈值改为按 `normalizedCategory` 分级。S2.5 早于市场元数据获取，此刻只有 `event`（含 `question`），因此用**纯字符串关键词分类**（无 API 调用）——把 `SmartWalletMarketStateService.resolveNormalizedCategory()` 的关键词匹配段抽成无依赖静态工具 `MarketCategoryClassifier.classifyByText(question)`，供 S2.5 复用。

新增配置：

```yaml
smart-wallet:
  signal-risk:
    max-ingest-signal-age-seconds: 10800        # 兜底/默认（OTHER 及未命中）
    max-ingest-signal-age-by-category:
      SPORTS: 600          # 10 分钟 —— 电竞/网球等快市场
      CRYPTO: 1800
      WEATHER: 1800
      CURRENT_EVENTS: 3600
      ENTERTAINMENT: 3600
      POLITICS: 10800
      MACRO: 10800
      BUSINESS: 10800
```

S2.5 改造伪代码：

```
String category = MarketCategoryClassifier.classifyByText(event.getQuestion());
long ingestMaxAgeMs = maxIngestSignalAgeMsFor(category);   // 查 map，未命中用默认
if (signalAgeMs > ingestMaxAgeMs) {
    createIngestStaleSkippedTask(event, signalAgeMs, ingestMaxAgeMs);
    return;
}
```

**涉及改动**：`SmartWalletFollowTaskService`（S2.5 段、`maxIngestSignalAgeMs()`）、`SmartWalletProperties.SignalRisk`（新增 map）、新增 `MarketCategoryClassifier`。

**风险**：关键词分类可能漏判（快市场误归 OTHER → 用 3 小时）。缓解：先用宽松分级值（SPORTS 用 20–30 分钟）灰度，再收紧。

**验证**：单测断言各 category 命中对应窗口；上线后观察 `follow_task` 中 `STALE` 上升、`MARKET_RESOLVED` 下降。

## 修复二（P0）：拦截任务写入细分 skip 标签

**对应问题 6.4** — `createLifecycleSkippedTask` 一律写 `primary_skip_reason=NON_TRADABLE`，DB 层无法区分 RESOLVED / NOT_ACCEPTING / CLOSED。

**当前状态**：❌ 未做。`SmartWalletFollowTaskService:1408-1409` 仍写死 `NON_TRADABLE` / `NON_TRADABLE`。

### 关键约束

`NON_TRADABLE` 被下游依赖：`SmartWalletFollowTaskService:424-425` 有 `if (buy && !"NON_TRADABLE".equals(primary))`；`:2303` 的 `primarySkipReason()` 固定词表也以 `NON_TRADABLE` 为首位。**因此不能把 `primary_skip_reason` 直接改成 `MARKET_RESOLVED`**。

### 方案

保留 `primary_skip_reason=NON_TRADABLE`（兼容下游），把细分原因放进 `skip_reason_tags`：

```
String reasonCode = marketState.blockingReasonCode();   // MARKET_RESOLVED / MARKET_NOT_ACCEPTING_ORDERS / MARKET_CLOSED
task.setPrimarySkipReason("NON_TRADABLE");
task.setSkipReasonTags("NON_TRADABLE," + reasonCode);
```

DB 端即可用 `skip_reason_tags LIKE '%MARKET_RESOLVED%'` 精确归因。

**涉及改动**：仅 `createLifecycleSkippedTask()`（`:1389-1422`）。无表结构变更（`skip_reason_tags` 为 varchar(512)）。

**风险**：极低。需确认是否有报表/前端按 `skip_reason_tags` 精确等值匹配 `"NON_TRADABLE"`——若有改为 `LIKE`。

**验证**：单测构造三种 `marketState`，断言 `skip_reason_tags` 内容；上线后直接按细分标签统计。

## 修复三（P1）：市场状态检查前移 + 降低端到端延迟

**对应问题 6.1** — 市场检查（S4）位于长链路末端，叠加 15–40 分钟摄取延迟，快市场走到 S4 时往往已结算。

**当前状态**：✅ 3A 已完成（2026-05-23）——市场状态检查已前移到 S3 候选增强之前，死市场在生成 candidate 前即被拦截。3B 端到端降延迟（WS 开关、轮询间隔）为配置/运营项，未改代码，建议按文档「风险从低到高」灰度。

### 3A. 市场状态检查前移到 S3 之前

在 S2.5 之后、S3 候选增强之前插入一次轻量 lifecycle 预检：

```
// S2.5 之后
SmartWalletMarketInfoEntity marketInfo = ensureMarketInfoForEvent(event);
MarketStateSnapshot marketState = refreshMarketState(event);
if (!marketState.isActive()) {
    createLifecycleSkippedTask(event, null /* candidate 尚未生成 */, marketInfo, marketState);
    markSourceEventProcessed(event);
    return;   // 不再进入 S3 候选增强
}
// 否则继续 S3，并把 marketState 透传给 S4/G6（见修复六）
```

`createLifecycleSkippedTask` 已支持 `candidate==null`（`:1395-1396`），前移可行；代价是 SKIPPED 任务缺 `entityId`/`followCandidateId`，对死市场记录可接受。

### 3B. 降低端到端延迟（治本）

按风险从低到高：① 缩短领单事件轮询周期（分钟级 → 15–30 秒），优先白名单钱包；② 启用 WebSocket 客户端（`enable-ws-client=true`），把延迟压到秒级，需先 test 环境灰度验证断线重连与积压重放；③ 快市场走独立高优先级处理队列，避免与历史回填抢单一调度线程。

**涉及改动**：`SmartWalletFollowTaskService`（链路顺序）、`PolymarketWebSocketClient` 及开关、轮询 Job 间隔。

**风险**：前移导致 candidate 为空的 SKIPPED 记录字段不全（可接受）；启用 WS 需先灰度，保留轮询兜底；缩短轮询/WS 都会加大 API 压力，需配合限流。

**验证**：监控 `trade_event.opened_at → follow_task.created_at` 延迟分位数，目标稳态 P50 < 2 分钟。

## 修复四（P1）：按 marketType 的分级时间过期判定

**对应问题 6.3** — `resolveLifecycle()` 不使用 `marketEndAt`；G6 的 2026-05-18 修复又把"endAt 已过"从拒绝条件中摘除，时间维度判定实质失效。

**当前状态**：⏸️ **待处理事项（由 Ray 后续处理，本批不实施）**。
修复四的方向是「交易侧对快市场重新启用 `endAt` 提前判死」，与监控侧《市场过期监控过滤修复方案》已采用的**方案 A**「信任 `lifecycle`、忽略 `endAt`」存在**设计方向冲突**（见本文第四节「待确认 #1」）。
此外，2026-05-23 实测发现 `SmartWalletMarketStateServiceTest.shouldTreatPersistedExpiredActiveSnapshotAsClosedUnresolved` 为预先失败用例——它断言「持久化 ACTIVE 但 endAt 过期 → 判 CLOSED_UNRESOLVED」，而现行 `resolvePersistedLifecycle` 不看 endAt；该用例与本修复四同属「endAt 过期契约」问题，应在修复四决策一并处置。
**须先确认「监控求稳 / 交易求准 是否允许并存不同标准」，再决定是否实施修复四。** 在此之前 G6 时间维度判定保持现状不动。

> 注意：监控视图侧已有一份独立修复（`市场过期监控过滤修复方案`，方案 A）决定"继续信任 lifecycle、忽略 endAt"。本修复四是**交易侧**的相反方向——仅对快市场重新启用 endAt。推进前需与监控侧的方案 A/B 决策对齐，避免设计不一致。

### 方案

引入按 marketType 分级的时间过期判定：长尾市场保持宽松，快市场用 endAt 提前判死。系统已有 marketType（`classifyMarket()` 产出 `FAST_EVENT` 等）。

```
// 仅对快市场启用 endAt 提前判死；长尾市场维持现状
boolean isExpiredByTime(MarketStateSnapshot s, String marketType, long graceMs) {
    Long endAt = s.marketEndAt();
    if (endAt == null || endAt <= 0) return false;
    if (!"FAST_EVENT".equals(marketType)) return false;   // 长尾市场不靠时间判死
    return System.currentTimeMillis() - endAt > graceMs;
}
```

G6 `remainingMs<=0` 分支改造：

```
if (remainingMs <= 0) {
    if (!isActive() || !acceptingOrders)              拒绝 G6_MARKET_EXPIRED;        // 原逻辑
    else if (isExpiredByTime(marketState, marketType, fastExpiryGraceMs))
                                                      拒绝 G6_MARKET_EXPIRED_FAST;   // 新增
    else                                              放行（[MARKET_END_AT_STALE_BUT_ACTIVE]）;
}
```

新增配置：`smart-wallet.signal-risk.fast-expiry-grace-ms: 300000`（5 分钟宽限）。

**关于 `resolveLifecycle`**：不要把时间逻辑塞进它——保持 lifecycle = API 客观事实，时间判定独立放在 gate 层，避免重新引入长尾市场误杀。

**涉及改动**：`SmartWalletSignalRiskService`（G6 分支）、新增 `isExpiredByTime`、`SmartWalletProperties.SignalRisk`（新增 `fastExpiryGraceMs`）。

**风险**：宽限值过小→临界点误杀，过大→失效，初值 5 分钟后调；依赖 `marketEndAt` 准确性，与修复五强相关。

**验证**：单测——快市场 endAt 已过 + lifecycle=ACTIVE → 命中 `G6_MARKET_EXPIRED_FAST`；长尾市场同条件 → 仍放行。

## 修复五（P1）：lifecycle 全量刷新 + 自适应缓存 + 不可靠标记

**对应问题 6.5** — 判定强依赖 `market_info` 数据新鲜度、60 秒缓存与 API 可用性；API 失败时回退到旧数据或 `unknown()=ACTIVE`。

**当前状态**：⚠️ 部分（2026-05-23）。**5A 已完成**——`MarketInfoEndAtRefreshJob` 由「只刷 endAt」升级为 lifecycle 全量刷新（改调 `marketStateService.refreshMarket(forceRefresh=true)`，回写 endAt/closed/acceptingOrders/resolvedOutcome/lifecycle）。**5B 已完成**——`SmartWalletMarketStateService` 缓存 TTL 由固定 60 秒改为按距结算时间自适应（≤10min 强制刷新 / ≤1h 用 15s / 其余 60s）。**5C 未做**——`metadataReliable` 不可靠标记涉及跨模块 record 字段改动 + 改变交易门行为（不可靠即不放行），留待单独评审。

### 方案

**5A. lifecycle 全量刷新**：把 `MarketInfoEndAtRefreshJob` 扩展为同时回写 `closed`/`acceptingOrders`/`resolvedOutcome`/`marketLifecycle`（或新增 `MarketLifecycleRefreshJob`）；重点扫描 `lifecycle=ACTIVE` 且 `endAt` 临近/已过的市场。

**5B. 自适应缓存 TTL**：

```
long ttl(MarketStateSnapshot s) {
    Long endAt = s.marketEndAt();
    if (endAt == null) return 60_000;
    long remaining = endAt - now;
    if (remaining <= 10*60_000) return 0;        // 临近结算：每次强制刷新
    if (remaining <= 60*60_000) return 15_000;   // 1 小时内：15 秒
    return 60_000;
}
```

**5C. 不可靠标记**：给 `MarketStateSnapshot` 增加 `metadataReliable` 标志；API 拉取失败且无可信持久化数据时置 `false`；gate 对不可靠市场保守处理（落"待重试" `G6_MARKET_STATE_UNRELIABLE`，而非当 ACTIVE 放行）。`unknown()` 同理标记不可靠。

**涉及改动**：`MarketInfoEndAtRefreshJob`、`SmartWalletMarketStateService`（缓存 TTL）、`MarketStateSnapshot`（新增字段）、gate 消费方。

**风险**：自适应缓存增加临近结算市场的 API 调用量，需配合限流；"不可靠即不放行"在 API 大面积故障时会压低开单量（PAPER 阶段无害，方向正确）。

**验证**：单测——metadata=null 且无持久化 → `metadataReliable=false` → gate 不放行；监控 lifecycle 刷新 Job 的 `updated` 计数。

## 修复六（P2）：单事件市场状态上下文复用

**对应问题 6.6** — 同一事件最多触发 4 次市场状态解析（`ensureMarketInfoForEvent:2013`、S4 `refreshMarketState:919`、G6 `refreshMarket:411`、endAt 为空时 forceRefresh）。

**当前状态**：✅ 已完成（2026-05-23）。市场检查前移后单事件只解析一次 `marketState`，并经新增的 5 参 `evaluate(..., preResolvedMarketState)` 透传给 G6 复用；G6 不再重复 `refreshMarket`。单事件市场状态解析次数已从 4 次降到约 2 次（`ensureMarketInfoForEvent` 内部 + 前移预检），符合文档「必要时 2 次」的验收口径。未引入独立 `MarketStateContext` 类——直接用参数透传快照，更轻量。

### 方案

按事件维度只解析一次，沿链路透传。做一个请求级 `MarketStateContext`（优先方法参数透传，不用 `ThreadLocal`，避免线程复用串味）：在修复三的"前移预检"点解析一次快照放入 context，S4/G6 直接复用；仅在 G6 真正决策临界点、且快照年龄超阈值（如 >30 秒）时才 forceRefresh 一次。把 4 次降到 1（必要时 2）次。

**涉及改动**：`SmartWalletFollowTaskService`、`SmartWalletSignalRiskService` 调用链与方法签名；新增 `MarketStateContext`。

**风险**：透传改动面较大，需保证 context 生命周期与单事件严格对齐；复用"稍旧"快照由"决策临界点按年龄强刷"兜底。

**验证**：日志埋点统计单事件 `refreshMarket` 实际调用次数，目标 ≤ 2；同批事件回放对比 S4/G6 判定结果与改造前一致。

## 修复七（P2）：停机积压批量排空快速通道

**对应问题 6.7** — 服务停机后事件积压，恢复时批量重放：超窗口的→STALE，未超窗口但市场已结算的→大量 `MARKET_RESOLVED`。

**当前状态**：✅ 已完成（2026-05-23）。源头侧缓解（`warmPromotionBackfillLookbackDays=2`）已有；新增 `SmartWalletFollowTaskService.drainStaleSignalBacklog()` 定时任务（默认 2 分钟一次）：扫描 `processed=0` 的 `trade_event`，对 `openedAt` 超「按市场类别分级」窗口者批量落 SKIPPED/STALE 并标记 processed，窗口内事件留给正常链路。

### 方案

修复一（分级窗口）落地后，快市场积压事件大多会被正确判为 STALE，本问题已大幅缓解。再补两点：

**7A. 启动期/积压期批量排空**：服务启动或检测到积压（待处理 `trade_event` 数量超阈值，或处理出现长时间断档）时，先批量预筛——对 `openedAt` 早于（分级）窗口的事件，直接批量落 SKIPPED/STALE，不逐条走完整 S1–S6 链路。

```
启动 / 积压检测 → 扫描 processed=0 的 trade_event
  → 按 category 分级窗口判定
  → openedAt 超窗口者：批量 UPDATE 落 SKIPPED/STALE，标记 processed
  → 仅窗口内的事件进入正常链路
```

**7B. 与运行报告联动**：停机本身应靠运行分析报告 P0（systemd 守护 + 自动重启）根治；本修复只是停机后的损害控制。

**涉及改动**：新增积压检测/批量排空逻辑（启动钩子 + 定时巡检）；复用修复一的分级窗口工具。

**风险**：批量落 STALE 属"宁可漏跟不可错跟"，方向安全；以 `openedAt` 为硬判据避免误伤窗口内有效事件。

**验证**：构造跨停机窗口的积压事件，验证超窗口者被批量 STALE、窗口内者正常处理；模拟 40 小时停机恢复，对比改造前后恢复耗时与 `MARKET_RESOLVED` 数量。
