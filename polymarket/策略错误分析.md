## 二、根因分析

### Bug-1【最严重】策略类型错配：跟的是「实时做市商」，用的是「方向预测」逻辑

**严重程度：Critical**

#### 问题描述

被跟钱包（如 RN1: `0x2005d16a`）实际上是**实时赛事流动性交易者**，他们的交易模式是：
1. 在赛事开始前买入看涨方（方向性押注）
2. 随着赛事进行，根据比分实时买入对立方向进行**动态对冲**
3. 最终两边都持仓，通过不对称的持仓比例锁定收益

以 THEMONGOLZ vs FUT ESPORTS (CS2 比赛) 为例，RN1 的完整操作：

```
00:52  买入 THEMONGOLZ @ 0.52-0.54，投入 $6,493  ← 我们跟了这一笔
00:58  买入 FUT ESPORTS @ 0.29，投入 $491         ← 开始反向对冲，我们没跟
01:03  买入 FUT ESPORTS @ 0.45-0.46，投入 $682    ← 继续对冲，我们没跟
01:04  追加 THEMONGOLZ @ 0.50，投入 $1,226        ← 继续加仓
01:30  大幅买入 FUT ESPORTS @ 0.35-0.41，投入 $5,504  ← THEMONGOLZ开始输，我们没跟
01:40  FUT ESPORTS @ 0.92，投入 $782             ← 反超押注已完成

结果: FUT ESPORTS 赢。THEMONGOLZ token → 0.09，FUT ESPORTS token → 0.92
RN1 实际结果: FUT ESPORTS 仓位收益覆盖 THEMONGOLZ 亏损 → 净盈利
我们的结果:  只有 THEMONGOLZ 仓位，亏损 -83%，没有对冲
```

| 维度 | 被跟钱包 (RN1) | 我们的策略 |
|------|-------------|---------|
| 交易腿数（同一市场） | 25 笔，双向动态调整 | 1 笔，固定方向 |
| 对冲机制 | 有（买反方向覆盖亏损） | 无（`block-opposite: true` 阻断） |
| 赛事结束后净结果 | 盈利（对冲保护） | -83% 裸亏 |

#### 根本原因

配置 `block-opposite-open-position-same-market: true` 把被跟钱包的「动态换边对冲」信号当作「冲突信号」拦截了。这是策略层的根本性设计错误：**对被跟钱包做了错误的行为假设（单向方向性持仓），实际上他们是多腿实时交易。**

#### 修复方案

1. 将赛事类市场（outcome 为队伍名/人名、`market_end_at` 在 24 小时内）单独识别，**暂时停止跟单此类市场**，仅跟宏观/政治类预测市场（YES/NO 结构）。
2. 长期：实现「换边检测」逻辑——当被跟钱包在同一市场发出反向买入信号，且该信号规模 > 原始信号 50% 时，视为调仓信号：自动平掉原有持仓 + 跟入新方向。

### Bug-2【严重】钱包筛选数据严重失真（幸存者偏差）

**严重程度：High**

#### 问题描述

数据库中所有被跟钱包的评分数据：

```
winRate: 1.0          ← 不可能是真实的
maxDrawdownRate: 0.0  ← 更不可能是真实的
```

这些数据来自 Polymarket **官方排行榜**。官方排行榜只展示每个钱包历史上**最盈利的 top-50 笔仓位**，不是全量数据。

**实际情况：**
- RN1 在今天刚产生了一笔 THEMONGOLZ 仓位（入场价 0.52，当前 0.09，浮亏 -83%）
- DrPufferfish：上次交易在 2026-03-25（17 天未活跃）
- SeriouslySirius：上次交易在 2026-01-04（**3 个月未活跃**）
- 0x006cc8：上次交易在 2026-01-28（2 个月未活跃）

用展示高光时刻的数据筛选跟单对象，等同于「看基金只看成立以来最高点的收益」。

#### 修复方案

1. 在 `smart_wallet_follow_task` + `smart_wallet_position` 表中自建评分体系，基于**内部真实跟单结果**计算实际胜率：

```sql
SELECT
  ft.wallet_address,
  COUNT(*)                                              AS total_follows,
  SUM(CASE WHEN p.realized_pnl_usdc > 0 THEN 1 ELSE 0 END) AS wins,
  AVG(p.realized_pnl_usdc)                             AS avg_pnl,
  MAX(ft.created_at)                                   AS last_signal_at
FROM smart_wallet_follow_task ft
JOIN smart_wallet_position p ON ...
WHERE ft.status = 'FOLLOWED'
GROUP BY ft.wallet_address;
```

2. 在 `SmartWalletProfileService` 中增加「活跃度惩罚」：超过 30 天未有新信号的钱包，`walletScore` 自动衰减 0.1/周，超过 90 天自动下线。

3. 对 `winRate = 1.0` 且 `totalTrades <= 50` 的钱包打「不可信」标记，不允许独立触发跟单。

### Bug-3【严重】组合上限过低导致策略实际停止运行

**严重程度：High**

#### 问题描述

当前 `max-open-positions`（组合持仓上限）为 **10**，已全部占满。

信号跳过记录中最高频的原因：
```
"Open position count has reached the portfolio limit."
```

结果：**策略实际上已停止执行新交易**，只是在被动等待这 10 个仓位结算。而这 10 个仓位中有 3 个是赛事市场，结算时间不确定；有 3 个已深度亏损。

#### 修复方案

**短期（立即操作）：**
- 手动平仓 THEMONGOLZ 两个持仓（当前亏损 -83% / -72%），止损释放持仓名额。
  - 平仓方式：调用 `/smart-wallet/clob/orders/{orderId}/cancel` 或直接卖出
  - 预期止损金额：~$46，但可释放 2 个名额恢复策略执行

**中期（配置修改）：**
```yaml
# application.yml
max-open-positions: 25       # 从 10 提升至 25
max-order-usdc: 50           # 从 30 适当提升
```

**长期（代码修改）：**
- 按市场类型分桶管理持仓上限：赛事类上限 5，宏观类上限 20
- 对同一市场的多笔持仓合并为一个位置计数

### Bug-4【中等】共识门槛与活跃钱包数量不匹配

**严重程度：Medium**

#### 问题描述

几乎所有被跳过的信号都包含：
```
"Consensus wallet count is below threshold."
"Consensus score is below threshold."
```

系统要求**多个被跟钱包同时发出同一市场的信号**才允许执行，但当前 watchlist 中大部分钱包已经数月未活跃，现实中只有 1-2 个钱包在活跃交易（主要是 RN1 和 swisstony）。

这导致共识门槛形同虚设地过滤掉了几乎全部信号。

#### 修复方案

```yaml
# application.yml
enable-consensus-gate: false          # 或
min-distinct-wallets: 1               # 降为1
enable-single-wallet-override: true
single-wallet-override-min-wallet-score: 0.78
single-wallet-override-min-win-rate: 0.55
single-wallet-override-min-trades: 20
```

同时：定期（每周）刷新 watchlist，替换掉超过 60 天未活跃的钱包。

### Bug-5【中等】无止损机制，亏损仓位长期占用名额

**严重程度：Medium**

#### 问题描述

策略进入持仓后没有任何止损逻辑，持仓只能等待：
1. 市场结算（YES/NO 最终结果）
2. 手动干预

对于赛事类市场，一旦预测方向错误，持仓价值会在比赛进行中快速归零（如 THEMONGOLZ 从 0.54 → 0.09），但策略持续持有直到结算，且该仓位继续占用名额阻止新机会进入。

#### 修复方案

在 `SmartWalletFollowTaskService` 的定时检查逻辑中新增止损触发：

```java
// 伪代码
if (position.getUnrealizedPnlRate() < -stopLossThreshold) {
    // 发出平仓信号
    submitSellOrder(position);
    position.setStatus("STOP_LOSS");
}
```

配置：
```yaml
enable-auto-stop-loss: true
auto-stop-loss-threshold-rate: 0.50   # 亏损50%触发（赛事市场波动大）
stop-loss-check-interval-minutes: 5
```

### Bug-6【低】费用跟踪缺失，盈亏数据不准确

**严重程度：Low**

#### 问题描述

数据库与 API 中，所有仓位的 `feeUsdc = 0`：

```json
"feeUsdc": 0.0
```

真实情况：Polymarket 对 taker 收取约 0.15% 手续费。$254 成交额对应约 **$0.38** 费用未被记录，导致盈亏数据略微偏乐观。

#### 修复方案

在 `LoggingPolymarketExecutionGateway` 中修改费用计算，从实际成交价反推：
```java
// 替换固定 0
BigDecimal fee = filledSize
    .multiply(properties.getEstimatedFeeRate())
    .setScale(8, RoundingMode.HALF_UP);
result.setFeeUsdc(fee);
```

## 四、核心结论

> **这些顶级钱包是「实时赛事流动性交易者」，不是「预测型持仓者」。**  
> 他们通过多腿动态对冲在赛事中锁定收益，跟单系统只复制了第一腿（方向性建仓），却缺失了关键的对冲腿。  
> 这不是参数调优问题，而是**策略假设的根本性错配**。  
> 短期解法：过滤赛事类市场，只跟宏观/政治预测市场。  
> 长期解法：实现多腿换边跟单，完整复制被跟钱包的交易结构。
