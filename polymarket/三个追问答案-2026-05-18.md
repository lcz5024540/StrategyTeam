# 三个追问的精确答案

---

## Q1：`0x2005d16a` 的小订单为什么没被合并？

**结论：合并是有的，且工作得很好。但合并后的 stake 不是问题——是 G6 市场过期把它们都拒了。**

### 实测数据

`0x2005d16a` 最近 6 小时的 follow_task 合并后 stake 分布：

| stake_bucket | 任务数 |
|--------------|--------|
| `>=$10` | **59** |
| `<$10` | 26 |
| `<$5` | 24 |
| `<$1` | 8 |
| `=$0` | 91 |

**59 个任务合并后金额 ≥ $10**，所以"小订单没合并"这个说法不准确。合并系统是工作的：

```text
最近 10 个任务:
task#101863  fragment_count=2  stake=$11.77  PAPER_SHADOW
task#101862  fragment_count=2  stake=$4.40   PAPER_SHADOW
task#101852  fragment_count=2  stake=$11.92  PAPER_SHADOW
...
intent_key 都正确分组到 marketId+outcome+side
```

### 那为什么还 PAPER_SHADOW？看 task 101863 的完整 reasons

```text
[MANUAL_ALLOWLIST_PASS] ...                        ← 白名单通过
[ARCHETYPE] NOISE_OR_INSUFFICIENT, OBSERVE_ONLY    ← 这是 reasons 文本, 不拒 (绕)
[BEHAVIOR] FAST_STOP_LOSS                          ← reasons, 不拒 (绕)
[LEADER_DRIFT_ACTIVE] cosineDistance=0.0365        ← 通过
Market is already at or past expected end time.    ← G6 命中 ⚠
[MARKET_TYPE] FAST_EVENT
[MANUAL_ALLOWLIST_FAST_EVENT_BYPASS] ...           ← 我加的 G7 bypass 起效
Kelly stake=23.77 (p=0.69 price=0.17)              ← Kelly 正 EV $23.77 — 是好信号！
SPIKE_STAKE ... 减仓
stake multiplier 0.5 → final $11.77

firstRejectGate = G6_MARKET_EXPIRED
```

**Kelly 算出 $23.77 正 EV**——这本是个该跟的好信号。**但 G6 在 G10 之前，先一步把它拒了。**

### 真相

| 维度 | 状态 |
|------|------|
| IntentAggregation 合并 | ✅ 100% 工作（每个 task 都有 intent_key + fragment_count=2-7） |
| 合并后 stake 够大 | ✅ 59 个任务 ≥$10 |
| Kelly EV | ✅ 多数是正 EV（如 $23.77） |
| G7 快事件绕过 | ✅ 我的 yml 改动生效（"MANUAL_ALLOWLIST_FAST_EVENT_BYPASS" 已触发） |
| **G6 市场已过期** | ❌ **真正卡点** — 我的 endAt 代码 fix 没救到这类（Polymarket 上游本身没 endAt） |

## Q2：老地址中其他白名单为什么没有订单？

**结论：他们都还在交易，但频率比 `0x2005d16a` 低很多。不是 0 活动，是稀疏活动。**

### 实测 5 个老白名单最后交易时间

```text
0x2005d16a  最后交易: 2026-05-17 23:48:22  ← 最活跃 (27分钟前)
0x9d84ce0306 最后交易: 2026-05-17 22:54:24  ← 中等 (~1.5h 前)
0xfbfd14dd4b 最后交易: 2026-05-17 21:03:29  ← 中等 (~3h 前)
0x51fd8f0358 最后交易: 2026-05-17 13:12:53  ← 慢 (~11h 前)
0x9f2fe025f8 最后交易: 2026-05-16 13:18:37  ← 很慢 (~35h 前)
```

### 进而："最后交易时间"和"是否有订单"的关系

部署后（22:56 → 00:01）trade_event 入库统计：

| 钱包 | 部署后 trade_event |
|------|-------------------|
| 0x2005d16a | **54** |
| 0x9d84ce0306 | 1 |
| 其他 3 个 | 0 |

`0x9d84ce0306` 和 `0xfbfd14dd4b` 都在最近几小时有过交易，但部署后 sync 周期才刚抓过一次（按 30 分钟轮转），没新动作就没新事件。

**`0x9f2fe025f8` 已经 35 小时没动**，可能短期内继续 dormant。

### 而即使他们交易，也会和 0x2005d16a 一样卡 G6

我看了 `0x9d84ce0306` 那 1 条事件生成的 task：同样的 G6/G10 系列拒因。**这 5 个老白名单**画像类似——都是 NOISE_OR_INSUFFICIENT 类、做小单 / 快事件市场——所以即使所有 5 个一起活跃，**单子也会被 G6 大量过滤**。

## Q3：`syncHotWalletTrades` 能否缩短到 15 分钟？

**结论：当前我们的钱包默认已经是 15 分钟，但实际观察到 30+ 分钟，因为 archetype 分类决定的。要进一步缩短只能改代码。**

### 代码层（`WalletArchetypeClassifierService.java`）

```java
private static final long HF_SYNC_INTERVAL_MS      = 30_000L;   //  30 秒
private static final long SWING_SYNC_INTERVAL_MS   = 120_000L;  //   2 分钟  
private static final long THEMATIC_SYNC_INTERVAL_MS = 300_000L; //   5 分钟
private static final long VALUE_SYNC_INTERVAL_MS   = 600_000L;  //  10 分钟
private static final long NOISE_SYNC_INTERVAL_MS   = 900_000L;  //  15 分钟  ← 我们的钱包
```

`PolymarketWalletDiscoveryService.dynamicTradeSyncIntervalMs`：
```java
long recommended = walletArchetypeClassifierService.recommendedSyncIntervalMs(...);
return Math.max(5_000L, Math.min(recommended, Math.max(baseline, recommended)));
// 简化 = max(5s, recommended)
```

**baseline (`wallet-trade-sync-min-interval-ms`) 实际没生效**——`recommended` 完全决定一切。

### 我们的钱包目前的间隔

- 5 个老白名单 + 7 个新白名单 = **12 个 HOT**，绝大多数 archetype 是 **NOISE_OR_INSUFFICIENT**
- 每个钱包 lastEventSyncAt 后等 **15 分钟** 才再次被 sync
- 单轮 cycle 内顺序 sync 12 个钱包，每个 100ms-50s 不等
- 实测观察到的 30+ 分钟是因为：上一次 sync 该钱包是 30 分钟前，但更早的间隔可能是 archetype 推荐为更长

### 缩短到 15 分钟以下的 3 种方法

| 方法 | 工作量 | 风险 |
|------|--------|------|
| **A. SQL 改运行时配置** `smart-wallet.polymarket.wallet-trade-sync-min-interval-ms` | 1 行 SQL | ⚠️ 因为代码用的是 `min(recommended, max(baseline, recommended))`，**baseline 其实被忽略**，所以这条不会真正缩短 |
| **B. 改 `NOISE_SYNC_INTERVAL_MS` 常量从 900_000 → 较小值** | 改 1 行 + 重新编译 | 影响所有 NOISE 类钱包 |
| **C. 改 `dynamicTradeSyncIntervalMs` 公式让 baseline 实际起作用**（`return Math.min(baseline, recommended)`） | 改 2 行 + 重新编译 | 让运行时配置真正起效（推荐） |

### 我推荐的做法：方法 C + 设 baseline=10 分钟

```java
// before:
return Math.max(5_000L, Math.min(recommended, Math.max(baseline, recommended)));
// → 等价 max(5s, recommended)

// after:
return Math.max(5_000L, Math.min(recommended, baseline));
// → 让 baseline 真正起到"上限"作用; 配置改 baseline=600_000 (10min) 立即生效
```

然后通过 strategy_runtime_config 表设：
```sql
UPDATE strategy_runtime_config 
SET config_value='600000' 
WHERE config_key='smart-wallet.polymarket.wallet-trade-sync-min-interval-ms';
```

这样既保留 archetype 的"快慢分类"语义（HF 仍然 30s 优先），又能用配置把上限拉到 10 分钟。

## 🔥 真正打开开单瓶颈的答案

**所有路径最后都指向同一个最深的根因 G6_MARKET_EXPIRED**：
- 即使合并工作 ✅
- 即使 stake 够大 ✅
- 即使 Kelly 正 EV ✅
- 即使 G7 快事件 bypass 生效 ✅
- 即使白名单地址全活跃 ✅
- **市场 endAt 数据不准 → G6 一刀切**

我的代码 fix 解决了一半（让 Polymarket 有 endAt 的市场流进来）。但 Polymarket 自己不给 endAt 的市场（"... before 2027" 这种），现在仍被 G6 当成"已过期"拒。

要彻底打开开单瓶颈，**需要改 SmartWalletSignalRiskService Gate 6 的语义**：

```java
// 现在 (line 421-440):
if (endAt > 0 && endAt - now <= 0) {
    firstRejectGate = "G6_MARKET_EXPIRED";  // ← 拒绝
}

// 改进 (建议):
if (endAt > 0 && endAt - now <= 0) {
    // 检查市场是否仍然 ACTIVE + accepting orders
    if (marketState.isActive() && marketState.acceptingOrders()) {
        // endAt 过期但市场仍开放交易 → 是数据问题, 不应拒绝
        reasons.add("[MARKET_END_AT_STALE_BUT_ACTIVE] endAt past but lifecycle=ACTIVE; accepting follow.");
    } else {
        firstRejectGate = "G6_MARKET_EXPIRED";  // 真的关了才拒
    }
}
```

这是 5 行代码改动，能解决 G6 一半的拒绝 —— 建议纳入下一批修复一并实施。
