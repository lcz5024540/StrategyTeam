**编写时间**：2026-05-23
**配套文档**：`市场过期判定逻辑梳理-2026-05-23.md`（问题编号 6.1–6.7 沿用该文）

## 修复一（P0）：摄取新鲜度窗口按市场类别分级

**对应问题 6.2** — 当前 S2.5 入口闸门用统一的 3 小时（`maxIngestSignalAgeSeconds=10800`），对寿命不足 1 小时的快市场过于宽松。

### 现状

`SmartWalletFollowTaskService.java:884-903` 的 S2.5 闸门调用 `maxIngestSignalAgeMs()`（`:1105`），返回固定 3 小时。事件 `openedAt` 在 3 小时内即放行到 S4。

### 方案

把单一阈值改为**按 `normalizedCategory` 分级**。难点在于 S2.5 早于市场元数据获取，此刻只有 `event`（含 `question`）。解决办法：复用已存在的**纯字符串关键词分类逻辑**（`SmartWalletMarketStateService.resolveNormalizedCategory()` 的关键词匹配段，无 API 调用），对 `event.getQuestion()` 做一次轻量分类。

建议把关键词分类抽成一个无依赖的静态工具方法（如 `MarketCategoryClassifier.classifyByText(question)`），供 S2.5 与原服务共用。

新增配置：

```yaml
smart-wallet:
  signal-risk:
    max-ingest-signal-age-seconds: 10800        # 兜底/默认（OTHER 及未命中类别）
    max-ingest-signal-age-by-category:
      SPORTS: 600          # 10 分钟 —— 电竞/网球等快市场
      CRYPTO: 1800         # 30 分钟
      WEATHER: 1800
      CURRENT_EVENTS: 3600
      ENTERTAINMENT: 3600
      POLITICS: 10800      # 长周期，保持 3 小时
      MACRO: 10800
      BUSINESS: 10800
```

S2.5 改造伪代码：

```
String category = MarketCategoryClassifier.classifyByText(event.getQuestion());
long ingestMaxAgeMs = maxIngestSignalAgeMsFor(category);   // 查 map，未命中用默认
if (signalAgeMs > ingestMaxAgeMs) {
    createIngestStaleSkippedTask(event, signalAgeMs, ingestMaxAgeMs);
    // 日志带上 category，便于后续调参
    return;
}
```

### 涉及改动

`SmartWalletFollowTaskService`（S2.5 段、`maxIngestSignalAgeMs()`）、`SmartWalletProperties.SignalRisk`（新增 map 字段）、新增 `MarketCategoryClassifier` 工具类。

### 风险

- 关键词分类可能漏判（把快市场误归为 OTRER → 用 3 小时窗口）。缓解：SPORTS 关键词表已较全；可先用**较宽松的分级值**（如 SPORTS 用 20–30 分钟而非 10 分钟）灰度，再逐步收紧。
- 误把长周期市场归为 SPORTS → 窗口过短，漏跟。影响可接受（漏跟优于无效跟），且可观测。

### 验证

- 单测：构造不同 category 的事件，断言命中对应窗口。
- 上线后对比 `follow_task`：`primary_skip_reason=STALE` 应上升、`MARKET_RESOLVED` 应下降；总 SKIPPED 量下降。
- 观察 1–2 天，按 category 统计窗口命中分布，调参。

## 修复二（P0）：拦截任务写入细分 skip 标签

**对应问题 6.4** — `createLifecycleSkippedTask` 一律写 `primary_skip_reason=NON_TRADABLE`，DB 层无法区分 RESOLVED / NOT_ACCEPTING / CLOSED。

### 现状与约束

`SmartWalletFollowTaskService.java:1408-1409`：

```
.setPrimarySkipReason("NON_TRADABLE")
.setSkipReasonTags("NON_TRADABLE")
```

**关键约束**：`NON_TRADABLE` 是一个被下游依赖的**粗分类**。`SmartWalletFollowTaskService.java:424-425` 有判断 `if (buy && !"NON_TRADABLE".equals(primary))`；`:2303-2336` 的 `primarySkipReason()` 也把 `NON_TRADABLE` 作为固定优先级词表的首位。**因此不能直接把 `primary_skip_reason` 改成 `MARKET_RESOLVED`**，否则破坏下游逻辑。

### 方案

保留 `primary_skip_reason=NON_TRADABLE` 不变（兼容下游），把细分原因放进 `skip_reason_tags`：

```
String reasonCode = marketState.blockingReasonCode();   // MARKET_RESOLVED / MARKET_NOT_ACCEPTING_ORDERS / MARKET_CLOSED
task.setPrimarySkipReason("NON_TRADABLE");
task.setSkipReasonTags("NON_TRADABLE," + reasonCode);
```

这样 DB 端可用 `skip_reason_tags LIKE '%MARKET_RESOLVED%'` 或 `GROUP BY skip_reason_tags` 精确归因，而下游对 `NON_TRADABLE` 的判断不受影响。

### 涉及改动

仅 `createLifecycleSkippedTask()` 一处（`:1389-1422`）。无 DB 表结构变更（`skip_reason_tags` 为 varchar(512)）。

### 风险

极低。唯一需确认：是否有报表/前端按 `skip_reason_tags` 精确等值匹配 `"NON_TRADABLE"`——若有，改为 `LIKE` 或前缀匹配即可。

### 验证

- 单测：分别构造 RESOLVED / 不接单 / CLOSED 三种 `marketState`，断言 `skip_reason_tags` 内容。
- 上线后即可在 DB 直接按细分标签统计，替代当前"靠 error_message 文本反查"的做法。

## 修复三（P1）：市场状态检查前移 + 降低端到端延迟

**对应问题 6.1** — 市场检查（S4）位于长链路末端，叠加 15–40 分钟摄取延迟，快市场走到 S4 时往往已结算。

本修复分两部分：(A) 把检查前移、快速失败，省掉无效重活；(B) 降低端到端延迟，治本。

### 3A. 市场状态检查前移到 S3 之前

**现状**：链路顺序为 S2.5 → S3 候选增强（`enrichAndSaveCandidate` `:907`）→ S4 市场检查（`:918`）。死市场也会先做一遍候选增强。

**方案**：在 S2.5 之后、S3 之前插入一次轻量 lifecycle 预检：

```
// S2.5 之后
SmartWalletMarketInfoEntity marketInfo = ensureMarketInfoForEvent(event);
MarketStateSnapshot marketState = refreshMarketState(event);
if (!marketState.isActive()) {
    createLifecycleSkippedTask(event, null /* candidate 尚未生成 */, marketInfo, marketState);
    markSourceEventProcessed(event);
    return;   // 不再进入 S3 候选增强
}
// 否则继续 S3 候选增强 …… 后续 S4 可复用 marketState（见修复六）
```

`createLifecycleSkippedTask` 已支持 `candidate==null`（`:1395-1396` 用了三元判空），因此前移可行；代价是该 SKIPPED 任务缺 `entityId`/`followCandidateId`。对"死市场跳过"这类记录，缺这两个字段可接受；若要保留，可在前移点先做一次轻量实体解析（不做完整增强）。

**收益**：死市场不再消耗候选增强、智能富集；同时 marketState 可一路透传给 S4/G6（与修复六协同）。

### 3B. 降低端到端延迟（治本）

**现状**：启动日志显示 `enable-ws-client=false`，Polymarket 实时推送关闭，只能轮询；稳态摄取延迟 13–16 分钟，高负载时约 40 分钟。

**方案**（按风险从低到高）：

1. **缩短轮询周期**：把领单事件轮询间隔下调（如从分钟级降到 15–30 秒），优先覆盖白名单钱包。成本是 API 调用量上升，需配合限流与退避。
2. **启用 WebSocket 客户端**：`enable-ws-client=true`，订阅白名单钱包/市场的实时成交推送，把延迟压到秒级。需验证 WS 客户端在当前版本的稳定性（断线重连、积压重放），建议先在 test 环境灰度。
3. **快市场优先通道**：对 SPORTS 等快市场事件走独立、高优先级的处理队列，避免与大批量历史回填/慢任务抢单一调度线程（与运行报告"调度线程隔离"建议相同）。

### 涉及改动

`SmartWalletFollowTaskService`（链路顺序调整）、`PolymarketWebSocketClient` 及其开关配置、轮询 Job 的间隔配置。

### 风险

- 检查前移：candidate 为空的 SKIPPED 记录字段不全——可接受或加轻量实体解析。
- 启用 WS：客户端稳定性未知，断线/积压处理需验证；务必先 test 环境灰度，保留轮询作为兜底。
- 缩短轮询/WS 都会增加 API 压力，需同步确认限流策略，避免触发 Polymarket 限频（日志中已有 ~48 次 API 失败）。

### 验证

- 检查前移：对比改造前后，死市场事件不再出现 S3 候选增强日志。
- 降延迟：监控 `trade_event.opened_at → follow_task.created_at` 的延迟分位数，目标稳态 P50 < 2 分钟。
- WS 灰度：观察断线重连次数、是否出现事件丢失/重复。

## 修复四（P1）：按 marketType 的分级时间过期判定

**对应问题 6.3** — `resolveLifecycle()` 不使用 `marketEndAt`；G6 的 2026-05-18 修复又把"endAt 已过"从拒绝条件中摘除，时间维度判定实质失效。

### 现状

- `SmartWalletMarketStateService.resolveLifecycle()`（`:461`）：完全依据 API 的 `resolvedOutcome`/`closed`/`acceptingOrders`，`marketEndAt` 参数未用。
- `SmartWalletSignalRiskService.java:424-435`：`remainingMs<=0` 时，只有 `!isActive() || !acceptingOrders` 才拒 `G6_MARKET_EXPIRED`，否则放行。
- 5-18 修复的本意正确——Polymarket **长尾市场** endAt 经常陈旧，不能一刀切拒。所以**不能简单回退**。

### 方案

引入**按 marketType 分级**的时间过期判定：长尾市场保持宽松，快市场用 endAt 提前判死。系统已有 marketType（`classifyMarket()` 产出 `FAST_EVENT`/`LONG_HORIZON`/标准型），也已有 `timeToExpiryExemptMarketTypes` 等机制（`:1253-1260`），可直接复用。

新增一个工具判定：

```
// 仅对快市场启用 endAt 提前判死；长尾市场维持现状
boolean isExpiredByTime(MarketStateSnapshot s, String marketType, long graceMs) {
    Long endAt = s.marketEndAt();
    if (endAt == null || endAt <= 0) return false;
    boolean fast = "FAST_EVENT".equals(marketType);   // 也可纳入 category=SPORTS
    if (!fast) return false;                          // 长尾市场不靠时间判死
    return System.currentTimeMillis() - endAt > graceMs;
}
```

G6 `remainingMs<=0` 分支改造：

```
if (remainingMs <= 0) {
    if (!isActive() || !acceptingOrders) {
        拒绝 G6_MARKET_EXPIRED;                       // 原逻辑
    } else if (isExpiredByTime(marketState, marketType, fastExpiryGraceMs)) {
        拒绝 G6_MARKET_EXPIRED_FAST;                  // 新增：快市场按时间提前判死
    } else {
        放行（[MARKET_END_AT_STALE_BUT_ACTIVE]）;      // 长尾市场维持宽松
    }
}
```

新增配置：

```yaml
smart-wallet:
  signal-risk:
    fast-expiry-grace-ms: 300000     # 5 分钟：快市场过 endAt 超此宽限即判死
```

**关于 `resolveLifecycle`**：建议**不要**把时间逻辑塞进 `resolveLifecycle`——保持 lifecycle = API 客观事实，时间维度的判定独立放在 gate 层（上面的 `isExpiredByTime`），职责清晰，也避免再次引入长尾市场误杀。

可选增强：在修复三的"前移预检"点，也对快市场调用 `isExpiredByTime` 做一次早退（此处 marketType 未必算出，可退化为 category=SPORTS 判定）。

### 涉及改动

`SmartWalletSignalRiskService`（G6 分支）、新增工具方法、`SmartWalletProperties.SignalRisk`（新增 `fastExpiryGraceMs`）。

### 风险

- 宽限值过小→快市场临界点误杀；过大→失去意义。建议初值 5 分钟，灰度后调。
- 依赖 `marketEndAt` 的准确性——与修复五强相关，需先确保快市场 endAt 新鲜。

### 验证

- 单测：快市场 endAt 已过 + lifecycle=ACTIVE → 命中 `G6_MARKET_EXPIRED_FAST`；长尾市场同条件 → 仍放行。
- 上线后监控 `G6_MARKET_EXPIRED_FAST` 命中量与对应市场是否确实已结算（抽样核对），确认无误杀。

## 修复五（P1）：lifecycle 全量刷新 + 自适应缓存 + 不可靠标记

**对应问题 6.5** — 判定强依赖 `market_info` 数据新鲜度、60 秒缓存与 API 可用性；API 失败时回退到旧数据或 `unknown()=ACTIVE`。

### 现状

- `MarketInfoEndAtRefreshJob` 每 10 分钟只刷 `market_end_at`（`:77-83`），**不刷 `closed`/`acceptingOrders`/`resolvedOutcome`**——已结算市场的 lifecycle 不会被这个 Job 纠正。
- `SmartWalletMarketStateService` 缓存固定 60 秒（`DEFAULT_METADATA_STALE_MS=60000`）。
- `buildSnapshot()`（`:318-323`）：metadata 为 null 且无既有行时，`closed=false / acceptingOrders=true` → ACTIVE。
- `MarketStateSnapshot.unknown()` 返回 ACTIVE——"未知=可交易"。

### 方案

**5A. lifecycle 全量刷新**：把 `MarketInfoEndAtRefreshJob` 扩展为同时回写 `closed`/`acceptingOrders`/`resolvedOutcome`/`marketLifecycle`（或新增一个 `MarketLifecycleRefreshJob`）。重点扫描 `lifecycle=ACTIVE` 且 `endAt` 临近/已过的市场——这些最可能已结算却未更新。

**5B. 自适应缓存 TTL**：缓存 TTL 随"距 endAt 远近"变化：

```
long ttl(MarketStateSnapshot s) {
    Long endAt = s.marketEndAt();
    if (endAt == null) return 60_000;
    long remaining = endAt - now;
    if (remaining <= 10*60_000) return 0;        // 临近结算：每次强制刷新
    if (remaining <= 60*60_000) return 15_000;   // 1 小时内：15 秒
    return 60_000;                                // 其余：维持 60 秒
}
```

**5C. 不可靠标记**：给 `MarketStateSnapshot` 增加 `metadataReliable` 标志。API 拉取失败且无可信持久化数据时置 `false`；gate 层对 `metadataReliable=false` 的市场**保守处理**——不直接当 ACTIVE 放行，而是落"待重试"（如 `G6_MARKET_STATE_UNRELIABLE`，可短延迟后重排），避免把"未知"误当"可交易"。`unknown()` 同理标记为不可靠。

### 涉及改动

`MarketInfoEndAtRefreshJob`（或新增 Job）、`SmartWalletMarketStateService`（缓存 TTL）、`MarketStateSnapshot`（新增字段）、`SmartWalletSignalRiskService`/`SmartWalletFollowTaskService`（消费不可靠标记）。

### 风险

- 自适应缓存会增加临近结算市场的 API 调用量——需配合限流；可只对白名单相关市场启用。
- "不可靠即不放行"在 API 大面积故障时会拉低开单量，但这是正确的保守取向（PAPER 阶段尤其无害）。

### 验证

- 单测：metadata=null 且无持久化 → snapshot `metadataReliable=false`；gate 不放行。
- 上线后监控 lifecycle 刷新 Job 的 `updated` 计数，以及临近结算市场的状态滞后时长。

## 修复六（P2）：单事件市场状态上下文复用

**对应问题 6.6** — 同一事件最多触发 4 次市场状态解析（`ensureMarketInfoForEvent`→refresh `:2013`、S4 `refreshMarketState` `:919`、G6 `refreshMarket` `:411`、endAt 为空时 forceRefresh）。

### 方案

按事件维度只解析一次，沿链路透传。建议做一个**请求级**（单事件处理周期内）的 `MarketStateContext`：

- 在修复三的"前移预检"点解析一次 `MarketStateSnapshot`，放入 context（方法参数透传，或 `ThreadLocal`/作用域 Bean）。
- S4、G6 直接复用 context 中的快照。
- **保留一处可控的强刷**：仅在 G6 真正做"开单 vs 拒绝"的决策临界点，且快照年龄超过阈值（如 > 30 秒）时才 forceRefresh 一次；其余复用。

这样把 4 次降到 1（必要时 2）次，既减少 DB 读与 API 调用，也消除重复逻辑带来的额外延迟。

### 涉及改动

`SmartWalletFollowTaskService`、`SmartWalletSignalRiskService` 的方法签名/调用链；新增 `MarketStateContext`。

### 风险

- 透传改动面较大，需保证 context 生命周期与单事件处理严格对齐，避免快照串用到别的事件。优先用方法参数透传而非 `ThreadLocal`，降低线程复用串味风险。
- 复用快照可能用到"稍旧"的状态——用上面的"决策临界点按年龄强刷"兜底。

### 验证

- 日志埋点统计单事件的 `refreshMarket` 实际调用次数，目标 ≤ 2。
- 回归：确保 S4/G6 的判定结果与改造前一致（同一批事件回放对比）。

## 修复七（P2）：停机积压批量排空快速通道

**对应问题 6.7** — 服务停机后事件积压，恢复时批量重放：超窗口的→STALE，未超窗口但市场已结算的→大量 `MARKET_RESOLVED`。

### 方案

修复一（分级窗口）落地后，快市场积压事件大多会被正确判为 STALE，本问题已大幅缓解。在此基础上再补两点：

**7A. 启动期/积压期批量排空**：服务启动或检测到事件积压（如待处理 `trade_event` 数量 > 阈值，或最近处理出现长时间断档）时，先做一次**批量预筛**——对 `openedAt` 早于（分级）窗口的事件，直接批量落 STALE，不逐条走完整 S1–S6 链路：

```
启动 / 积压检测 → 扫描 processed=0 的 trade_event
  → 按 category 分级窗口判定
  → openedAt 超窗口者：批量 UPDATE 落 SKIPPED/STALE，标记 processed
  → 仅窗口内的事件进入正常链路
```

**7B. 与运行报告联动**：停机本身应靠运行分析报告 P0（systemd 守护 + 自动重启）来根治；本修复只是停机发生后的损害控制。两者配合，积压规模与处理成本都能压下来。

### 涉及改动

新增积压检测/批量排空逻辑（可作为启动钩子 + 定时巡检）；复用修复一的分级窗口工具。

### 风险

- 批量落 STALE 属"宁可漏跟不可错跟"，方向安全；唯一要避免误伤窗口内的有效事件——以 `openedAt` 为硬判据即可。

### 验证

- 构造一批跨越停机窗口的积压事件，验证超窗口者被批量 STALE、窗口内者正常处理。
- 模拟 40 小时停机恢复，对比改造前后恢复耗时与 `MARKET_RESOLVED` 数量。
