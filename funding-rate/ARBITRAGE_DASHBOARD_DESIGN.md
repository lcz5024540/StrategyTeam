# 套利策略 Dashboard：跨交易所 + 同一交易所设计与实施计划

> 状态：设计完成，待实施  
> 范围：只读观察与 Paper 验收；不在本期增加实盘开关、资金划转或下单入口。

## 0. 参考 PerpDexList 后的设计修订

参考页面：[PerpDexList 套利扫描器](https://perpdexlist.com/arbitrage)。它的优势不是更复杂，而是把“发现机会”压缩成一张立即可读的扫描表：两个模式切换、双腿并列、倒计时、可排序的开仓价差、流动性字段、历史实际资金费和全局筛选在同一屏完成。

### 0.1 借鉴的功能

| 参考站能力 | 本 Dashboard 的对应设计 | 与执行策略的差异 |
|---|---|---|
| `价格套利：永续-永续` / `资金费套利：永续-永续` 两个模式 | 增加“跨所价格扫描”和“跨所资金费扫描”两个主 Tab；同所套利为第三个 Tab | 跨所价格扫描首版只观察，不开放 Paper 开仓；跨所资金费才接入当前 Paper 路径 |
| 双腿逐行并列 | A/B 两腿固定展示：交易所、标准/原始合约名、价格、资金费、结算周期/倒计时 | 额外显示真实 long/short 方向，避免只看差值不知谁该多空 |
| 价格差、资金费差、年化、历史实际资金费 | 首屏保留“毛差、成本、单次净收益、可选年化等效、24h/7d/30d 实际累计资金费” | 排序默认使用**下一同步结算净收益**，不使用年化，防止不同 1h/4h/8h 周期误导 |
| 双边 24h 成交量与 OI | 在机会表中并列显示两腿 24h volume、OI，并支持分别设最小值 | 这些是流动性代理；真正可执行容量仍以 L2 共同基础币数量为准 |
| 币种/交易所/数值区间筛选 | 全局筛选条：币种、交易所、策略模式、状态、最低 volume/OI、最低容量、开仓价差、资金费差、净收益、结算时间偏差 | 所有筛选作用于完整结果集而非当前页 |
| 自动刷新与倒计时 | 显示“数据时间 + 下次刷新倒计时 + 每所最新报价年龄” | 数据过期时降低可信度，不将旧值当作实时值 |
| 可复制链接 | 将筛选和排序编码到 URL query；支持分享同一个只读研究视图 | 不在 URL 放任何仓位、账户或服务器信息 |
| 缺订单簿组合统计 | 显示“总组合 / 可展示 / 被隐藏”及原因：缺合约、缺 L2、报价过期、结算不同步、交易所不可用 | 被隐藏不等于不存在机会，必须可追溯原因和数量 |

### 0.2 相比原设计新增或强化的遗漏项

1. **市场扫描器优先于运营总览。** 原设计先列卡片和详情，缺少类似参考站的一屏机会矩阵。调整为默认打开“机会扫描”，总览退为辅助入口。
2. **跨所价格套利视图。** 即使当前 V1 只执行资金费套利，也应观察 perp-perp 价格偏差；它能解释资金费策略的 basis 风险，并为后续策略积累数据。该 Tab 必须标记 `OBSERVE_ONLY`。
3. **历史实际资金费。** 加入每个交易所腿的 24h / 7d / 30d 已结算累计资金费，而不只显示当前预测 funding；避免追逐短暂尖峰。
4. **市场流动性代理。** 增加两腿 24h 成交量和 OI 的显示/筛选；当前 L2 深度只能说明短时可成交量，不能替代全天流动性。
5. **扫描覆盖度。** 显示“发现的合约、可配对组合、因何被排除的组合、当前分页位置”，不能只有 Qualified 列表。
6. **研究工作流。** 增加保存/复制筛选链接、排序和用户 watchlist（后者在有用户体系后实施）。
7. **单一标准的双腿字段。** 所有扫描模式统一先呈现 A/B 原始事实，再呈现派生收益；不只显示一个抽象的 spread。

### 0.3 不直接照搬的部分

- 参考站的“年化”适合作为研究辅助，但我们的执行排序不能依赖年化，因为 1h、4h、8h 资金费的下一次结算和兑现概率不同。
- 参考站展示的报价价差不是指定下单规模下的成交成本；我们的主字段必须是 L2 VWAP、共同基础币数量、费用后净收益和可成交 basis。
- 参考站覆盖大量交易所和组合；当前 CoinStrategy 只接入四所，必须显式显示覆盖范围，而不是用稀疏数据假装全市场。

## 1. 目标与边界

一个看板回答四个问题：

1. **现在有没有可做的套利？** 区分跨交易所资金费套利与同一交易所期现/合约套利。
2. **若执行，真实可成交的规模和收益是多少？** 使用 L2 VWAP、手续费、滑点、资金费结算时间和容量，而非只看 Mark Price。
3. **正在持有什么风险？** 看到两腿是否对冲、下一次资金费、净敞口、容量、风控状态和异常原因。
4. **为什么没有机会或没有开仓？** 同时呈现拒绝原因、行情质量和交易所可用性，例如 Binance 的 HTTP 451。

边界：

- Web 层只读数据库中的看板读模型；**不直连 Job 的 8083 内网端口**，不读取原始 CSV 作为在线查询源。
- 数据刷新由 Job 写库，Web 以 5–10 秒轮询读库；历史图表使用分钟/小时聚合表。
- 首版只展示 Paper 状态。暂停、扫描、Paper 开仓等操作保留在受保护的运营接口，不放在首版首页。
- 所有百分比明确标注单位和口径：单次结算、小时化、年化不可混用；所有时间同时说明北京时间/UTC。

## 3. 页面设计

### 3.1 总览页

首屏固定为六张卡和两个列表：

| 区块 | 展示内容 | 目的 |
|---|---|---|
| 可执行机会 | 跨所/同所各自的数量、最佳净收益、最大可成交名义金额 | 快速判断是否有值得关注的机会 |
| 当前 Paper 持仓 | 数量、总名义金额、净 Delta、下次结算倒计时 | 识别持仓暴露 |
| 预计收益 | 下一结算预估资金费、开平费、滑点、净额 | 防止只看资金费差而忽略成本 |
| 风控状态 | pause、circuit、裸仓、超时、结算时间错配数 | 明确是否允许继续观察/开 Paper 仓 |
| 行情质量 | 各交易所健康、最新报价年龄、成功率、L2 深度覆盖 | 解释数据可信度 |
| 数据集 | 当日快照数、采集时长、磁盘使用、回放最近结果 | 支撑 7 天 Paper 验收 |

下方展示：

- **机会榜**：默认按“下一次同步结算净收益 × 可成交名义金额”排序，支持跨所/同所切换。
- **风险与异常流**：最近 20 条拒绝、行情失败、熔断和强制平仓事件；按严重度排序。

### 3.2 默认页：机会扫描器

采用参考站的“扫描器优先”布局，但对执行所需事实更严格。

```text
[跨所价格] [跨所资金费] [同所期现/永续]        下次刷新倒计时 · asOf 12:34:56 UTC
[币种搜索] [交易所多选] [流动性] [收益] [结算] [更多筛选] [复制链接]
总组合 N | 已展示 N | 可执行 N | 缺 L2 N | 过期 N | 不可用交易所 N
------------------------------------------------------------------------------------------------
币种 | A 腿（交易所/合约） | B 腿（交易所/合约） | 资金费/倒计时 | VWAP/报价 | 价差 | 净收益 | 容量 | 24h/7d/30d | 状态
------------------------------------------------------------------------------------------------
...
```

三个 Tab 共用搜索、筛选、排序、分页和 URL 状态；列按模式切换：

| Tab | 排序默认值 | 必须显示的核心列 | 状态 |
|---|---|---|---|
| 跨所价格 | 指定规模下的可成交价差（费用前后均可见） | A/B bid-ask VWAP、开仓价差、双边 volume/OI、L2 容量、历史价差 | `OBSERVE_ONLY` |
| 跨所资金费 | 下一同步结算净收益 × 可成交名义金额 | A/B funding、周期、倒计时、历史实际资金费、成本、净收益、VWAP basis、容量 | `PAPER_READY` / `REJECTED` |
| 同所期现/永续 | 单次净收益与风险调整后的资本效率 | 现货/合约、funding、basis、杠杆、保证金、费用、容量、下一结算 | `PAPER` / `LIVE`（未来） |

筛选应包含：

- 双边最小 24h 成交量、最小 OI；
- 最小 L2 可成交名义金额；
- 开仓价差范围、资金费差范围、净收益范围、成本覆盖倍数；
- funding 结算周期、下一结算偏差、倒计时范围；
- 是否只看 L2 完整、只看同币种同稳定币结算、是否显示被拒机会；
- 交易所健康状态、币种、观察列表。

### 3.3 跨交易所资金费套利页

#### A. 可执行机会表

每一行是 `币对 + 多头交易所 + 空头交易所 + 下一结算时间` 的一个方向，不能把反向方向合并。

| 字段 | 计算/来源 |
|---|---|
| 币对、方向 | Long 低资金费交易所 / Short 高资金费交易所 |
| 两侧原始资金费率 | 下一次实际结算的 raw funding rate，并显示各自结算周期 |
| 下一结算与偏差 | 两边时间、偏差秒数、是否在允许窗口 |
| 毛收益 / 成本 / 净收益 | `高方资金费 - 低方资金费 - 两边开平 taker 成本 - basis buffer` |
| 成本覆盖倍数 | `毛收益 ÷ 成本`，与 1.25 阈值对照 |
| Long ask VWAP / Short bid VWAP | 针对可成交共同基础币数量计算，附最优价偏离 bps |
| 可成交 basis | `(short VWAP - long VWAP) / long VWAP` 的绝对值与阈值 |
| 可成交名义金额 | L2 共同基础币数量对应的长腿实际名义金额 |
| 稳定窗口 | 当前方向已连续稳定的时间 / 所需时间 |
| 状态 | Qualified、Approved、Rejected；Rejected 必带原因 |
| 数据新鲜度 | 两边 funding/book 接收时间与毫秒年龄 |
| 24h / 7d / 30d 实际资金费 | 两腿各自已结算的累计资金费；缺数据显式显示 `—` |
| 市场流动性代理 | 两腿 24h 成交量、OI；只作筛选/风险参考 |

筛选器：币对、交易所、状态、最低净收益、最低容量、是否仅同步结算、是否只看 L2 完整机会。

#### B. 机会详情抽屉

- 左右两腿报价阶梯：前 20 档价格、USDT 名义金额、累计容量；高亮计划成交部分。
- 从资金费差到净收益的瀑布图：`资金费差 → 手续费 → 滑点/缓冲 → 净收益`。
- 同一方向的 24 小时序列：资金费、可成交 basis、容量、通过/拒绝状态。
- 拒绝原因时间线：例如 `SETTLEMENT_TIME_SKEW`、`COST_COVERAGE_BELOW_THRESHOLD`、`EXECUTABLE_BASIS_DEVIATION`。

#### C. 跨所 Paper 持仓

| 维度 | 内容 |
|---|---|
| 对冲完整性 | 长/短腿已成交数量、数量差、净 Delta、裸仓持续时间 |
| 收益归因 | 资金费、价差 PnL、开仓费、平仓费、滑点、合计 |
| 结算 | 已结算次数、下一次结算倒计时、两边结算状态 |
| 生命周期 | 创建、两腿开仓、补偿、监控、平仓的事件时间线 |
| 风控 | 当前 basis、mark 偏差、最大持仓时长、强制退出原因 |

### 3.4 同一交易所套利页

首版定义为“同一交易所的现货多 + 永续合约空”的资金费/基差套利；未来可扩展交割合约，不与跨所路径混合统计。

| 区块 | 展示内容 |
|---|---|
| 当前机会 | 交易所、现货/合约币对、资金费、现货-合约基差、预估净收益、可用额度、杠杆 |
| 持仓 | 现货数量、合约数量、两腿成交均价、名义金额、下一结算、状态 |
| 资金费与基差 | 入场/当前资金费，入场/当前基差率，持仓期间变化 |
| 收益归因 | 已实现 PnL、累计资金费、交易费、估计滑点、未实现基差 PnL |
| 风险 | 保证金率、杠杆、价格偏离、再平衡状态、止损/退出原因 |

同所页面必须显示“资金费是**收到还是支付**”，不能仅展示绝对值；若 funding 为负且策略方向不适配，应明确标为不可开仓。

### 3.5 数据质量页

这是 Paper 验收的必要页面，而不是运维附属页。

- 每所：健康状态、最近成功/失败、失败类型、连续失败次数、P50/P95 延迟、最近报价年龄。
- 每币对/交易所对：采集覆盖率、L2 完整率、可成交容量分布、结算时间偏差分布。
- 扫描覆盖：已发现合约数、理论配对数、已显示数、按排除原因分组的隐藏数。
- 数据集：UTC 文件数、行数、成功/失败比例、磁盘余量、最近回放文件与通过率。
- 明确标识受限来源，例如“Binance：HTTP 451，已排除出可执行机会计算”，避免把缺失数据误读成零机会。

## 4. 统一指标口径

| 指标 | 定义 | 禁止的误读 |
|---|---|---|
| 单次净收益率 | 下一同步结算原始资金费差减去开平成本和 basis buffer | 不年化、不按小时化后与单次值混排 |
| 可成交名义金额 | 两腿 L2 共同基础币数量下，长腿 VWAP 对应的 USDT 金额 | 不能取两边聚合深度的较小 USDT 数直接当 Delta-neutral 容量 |
| 可成交 basis | 相同基础币数量下的 short bid VWAP 与 long ask VWAP 差异 | 不用 Mark Price 替代 |
| Paper 总收益 | 已结算资金费 + 已实现价差 PnL - 已知费用/滑点 | 必须标注 `PAPER_PUBLIC_ESTIMATE` |
| 成功率 | 满足所有准入条件的机会数 ÷ 已评估方向数 | 与“实际开仓胜率”分开 |
| L2 完整率 | 同一快照两腿均保存至少一档有效深度的比例 | 不把 v1 回放数据算为完整 L2 |

## 5. 技术架构与读模型

```text
交易所公共行情 ──> Funding Job ──> 原始 CSV（审计/回放）
                               └──> MySQL 看板读模型 ──> Web API ──> Dashboard
同所订单/仓位/结算 ────────────────> MySQL 既有表 ────────┘
```

Web 与 Job 继续保持无 HTTP 依赖。Web 通过已有数据库连接读取聚合结果；Job 只负责写入事实与快照。

### 5.1 现有可复用数据

- 同所：`single_exchange_arbitrage_position`、`single_exchange_arbitrage_order`、`single_exchange_arbitrage_funding_settlement`，Web 的 `StrategyProductQueryService` 已经接入。
- 跨所：`cross_exchange_arb_opportunity`、`cross_exchange_arb_position`、`cross_exchange_arb_order`、`cross_exchange_funding_settlement`、风险快照及 v2 CSV。
- 现有 Web 路径：`/strategy-platform/strategy` 已有统一策略产品入口，可扩展而不另建平行首页。

### 5.2 本期需要补齐的读模型

现有跨所机会表没有保存 VWAP、L2 容量、可成交 basis、稳定时长、行情年龄、每所健康状态、24h volume/OI 与历史实际资金费；CSV 又不适合在线查询。因此新增以下只读投影：

1. `arbitrage_dashboard_snapshot`（每 5–10 秒 upsert）
   - 维度：`strategy_kind`（`CROSS_EXCHANGE_FUNDING` / `SINGLE_EXCHANGE_SPOT_FUTURES`）、币对、方向、交易所对、采集时间。
   - 值：资金费、结算时间/偏差、VWAP、basis、容量、成本、净收益、稳定窗口、状态/拒绝原因、行情年龄、数据完整度、24h volume、OI、历史实际资金费。
2. `arbitrage_dashboard_position_snapshot`（每分钟或状态变更写入）
   - 维度：策略类型、position code、时间。
   - 值：名义金额、双腿数量、净 Delta、下一结算、收益归因、风险状态。
3. `arbitrage_market_health_snapshot`（每分钟）
   - 维度：交易所、时间。
   - 值：健康、成功/失败/限流次数、延迟、最后错误分类、数据覆盖率。
4. `arbitrage_dashboard_daily`（每日聚合）
   - 用于 7/30 天趋势、机会通过率、收益归因与数据质量，不扫描 CSV。

保留原始 CSV 7–14 天用于重放；看板表只保存可查询的摘要。建议快照明细保留 30 天、分钟聚合 180 天、日聚合长期保留。

新增行情采集字段时，`PerpetualMarketDataClient` 需扩展统一的 ticker / OI DTO；某交易所没有可靠的 OI 或 24h volume 时返回 `null`，前端显示 `—`，不能以零代替。

## 6. Web API 契约

**前端归属**：页面源码和构建产物只放在 `docs/projects/CoinStrategy/coin-strategy-frontend`（React/Vite）；`coin-strategy-web` 只提供下列只读交互 API，不再托管套利扫描器静态页面。Web 服务存在 context path `/strategy/api`；Controller 以 `/strategy-platform/arbitrage-dashboard` 为前缀，因此以下为对外完整只读 API：

| API | 说明 |
|---|---|
| `GET /strategy/api/strategy-platform/arbitrage-dashboard/overview?window=24h` | 总览卡、两种策略摘要、数据质量摘要 |
| `GET /strategy/api/strategy-platform/arbitrage-dashboard/opportunities?kind=CROSS_EXCHANGE_FUNDING&symbol=&status=&minNetYield=&minNotional=` | 分页机会列表 |
| `GET /strategy/api/strategy-platform/arbitrage-dashboard/opportunities/{id}` | 机会详情、L2 摘要、收益瀑布、状态时间线 |
| `GET /strategy/api/strategy-platform/arbitrage-dashboard/positions?kind=&status=` | 两类策略统一持仓列表 |
| `GET /strategy/api/strategy-platform/arbitrage-dashboard/positions/{positionCode}` | 双腿、结算、风险与收益归因 |
| `GET /strategy/api/strategy-platform/arbitrage-dashboard/timeseries?kind=&metric=&symbol=&window=24h` | 图表序列，服务端下采样 |
| `GET /strategy/api/strategy-platform/arbitrage-dashboard/market-health?window=24h` | 交易所健康、延迟、失败原因与覆盖率 |
| `GET /strategy/api/strategy-platform/arbitrage-dashboard/data-quality?window=7d` | CSV/回放覆盖与 L2 完整率 |

API 返回必须携带：`asOf`、`timezone`、`source`（`PAPER_PUBLIC_ESTIMATE` 等）、`partial`、`missingExchanges`。前端遇到 `partial=true` 时显示黄色数据质量提示，不把空值填为 0。

## 7. 交互与权限

- 默认 10 秒自动刷新；图表默认 1 分钟粒度，用户主动查看时才加载深度详情。
- 首版只读，不在表格里提供“开仓”按钮；防止把研究/验收看板误变成交易终端。
- 若后续加入 Paper 操作，只允许管理员走单独确认弹窗：显示重报价结果、可成交名义金额、两腿 VWAP、下一结算和风险检查，不复用列表中的旧快照。
- 可导出 CSV 的内容仅限汇总指标和已脱敏的行情摘要；不得导出服务器路径、密钥、完整交易所错误响应。

## 8. 实施计划

| 阶段 | 工作项 | 交付与验收 |
|---|---|---|
| P0：扫描器口径冻结（1–2 天） | 确定三种 Tab、排序、筛选、年化显示规则、隐藏原因和时区；用 10 个固定案例核对 | 产品、策略、后端共同确认指标字典 |
| P1：跨所读模型（3–4 天） | migration、快照写入、健康投影、L2/VWAP、volume/OI、历史资金费与拒绝原因持久化 | Job 每个扫描周期写入；不读 CSV；断档显式标识 |
| P2：同所统一投影（2–3 天） | 从既有 position/order/settlement 聚合成同一 DTO 与收益归因 | 同所/跨所可用一个持仓列表和时间线组件展示 |
| P3：Web 只读 API（2–3 天） | 查询服务、分页/筛选、服务端聚合、权限和 API 测试 | Web 不访问 Job 端口；查询 P95 < 500ms（常用窗口） |
| P4：Dashboard UI（4–5 天） | 默认机会扫描器、总览、详情抽屉、持仓页、健康页、URL 筛选状态、空态/降级态 | 10 秒刷新无跳闪；缺失交易所和数据过期可见 |
| P5：验收与调优（7 天并行） | 用真实 Paper 采集验证，校对 CSV/DB/页面一致性，回放历史 | 7 天覆盖率、收益口径、异常解释均可追溯 |

实施顺序必须是 **P0 → P1/P2 → P3 → P4 → P5**。不建议先做前端静态图：当前跨所 L2、volume/OI、历史资金费和健康数据尚未持久化，先建读模型才能避免后续重写。

## 9. 首版验收清单

- [ ] 任何跨所机会都能追溯到两边资金费、结算时间、L2 VWAP、容量、成本与拒绝原因。
- [ ] 同所持仓能看到现货与合约两腿及资金费/基差/费用三类收益。

- [ ] 页面上的可成交容量与 Paper 执行使用相同的共同基础币数量算法。
- [ ] 页面显示 Paper/估算来源，不能被误解为真实账户账单。
- [ ] Web 无法访问 Job 内网端口，且所有首版接口均为只读。
- [ ] 7 天 Paper 数据可从看板查看覆盖率、通过率、收益分布和主要拒绝原因。
