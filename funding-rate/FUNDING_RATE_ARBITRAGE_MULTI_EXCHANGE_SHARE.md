# 多交易所资金费率套利实施进度

本文档仅记录“多交易所套利”的当前状态、差距分析和实施规划。

## 1. 当前状态

### 1.1 结论

* 当前仓库**尚未实现**多交易所套利的正式执行链路。
* 现有实现仍集中在“单交易所期现套利”。
* 多交易所套利目前属于方案设计、组件规划和后续开发任务。

### 1.2 已具备的可复用基础

虽然尚未落地多交易所执行链路，但现有仓库已经有部分能力可复用：

* 已有资金费率监控思路和风控分层方式。
* 已有并发双侧下单和回滚处理思路，可迁移到跨所执行器。
* 已有单交易所的保证金风控和再平衡框架，可扩展为跨所版本。
* 已具备部分 Binance / OKX 等交易所客户端基础能力。

## 2. 尚未完成的关键能力

### 2.1 交易所适配层未统一

* 多交易所套利首先需要统一不同交易所的：
    * funding 数据
    * 价格与盘口数据
    * 下单接口
    * 账户与保证金信息
* 当前尚未形成完整统一的适配层。

### 2.2 funding spread 监控未实现

* 尚未实现跨交易所 funding spread 的实时计算与排序。
* 尚未实现“候选交易所对”的实时扫描与筛选。

### 2.3 跨所双侧执行未实现

* 尚未实现跨交易所同时开仓的执行器。
* 尚未实现一侧成交、另一侧失败时的跨所回补逻辑。

### 2.4 资金调度与保证金补给未实现

* 尚未实现跨所资金分配。
* 尚未实现极端行情下的跨所补保证金与应急降杠杆。

### 2.5 风控模型未建立

* 尚未系统处理：
    * 交易所信用风险
    * 提现/划转风险
    * funding 结算机制差异
    * API 宕机或限仓风控

## 3. 建议实施路线

### 3.1 第一阶段：监控先行

1. 统一 Binance、OKX、Gate.io 等交易所 funding / price / book / account 数据结构。
2. 实现跨所 funding spread 实时监控。
3. 输出理论开仓点、理论净收益和候选交易所对。

### 3.2 第二阶段：模拟执行

1. 仅记录模拟双侧开仓和平仓结果。
2. 评估跨所价差、滑点、结算差异和资金占用成本。
3. 验证哪些交易所组合具备稳定可执行性。

### 3.3 第三阶段：小资金实盘

1. 先实现最小闭环版本，只支持少数交易所对。
2. 先使用极小仓位验证跨所下单与回补逻辑。
3. 建立完备告警和人工接管机制后再放大资金。
